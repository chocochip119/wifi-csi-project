# G-02 검증 구성과 판정 규칙

2026-09-26. 신규 소스는 `tb/tb_golden_encoder.v` 하나다. 기존 RTL/TB/FC stub/golden은 읽기 전용이다.
실제 비교 결과는 `G-02_구현_검증기록.md`에 별도로 기록한다.

## 구현 전 보정한 해석

- 유한한 입력의 일치는 해당 사례의 수치 일치다. 모든 입력·재학습 모델의 함수 등가성까지 증명하지 않는다.
- H6용 zero golden은 G-01 도구 세 파일을 scratch로 복사해 생성한다. 기존 `golden/src`를 다시 쓰지 않는다.
- FC는 기존 `fc_stub`을 수정 없이 둔다. 내부 RAM 검사 모드는 끄고 TB가 stub의 기존 `flat_raddr` 출력 reg에 주소만 구동한다.
  FIFO·FC start/done은 기존 모형 동작으로 INFER를 종료시키며, 모형 pose는 golden 판정에 사용하지 않는다.
- H4 불일치는 최초 오류에서 fatal로 중단하지 않는다. 384 word 전체, 같은 입력 반복, 다른 입력, H5를 끝낸 뒤 결과를 명시한다.
  제어/파일/프로토콜 실패는 별도의 fatal이며, 이 경우 전량 수집이 완료됐다고 보고하지 않는다.

## H1 파일 동일성

호스트 runner가 현재/zero 두 manifest의 `status=COMPLETE`를 확인하고 다음 SHA-256을 각각 대조한다:
blob ↔ manifest.blob.sha256, 입력 ↔ manifest.input.sha256, hex ↔ manifest.dumps.encoder_flat_u64.hex.sha256.
실제 TB가 읽을 파일을 simulation cwd로 byte 그대로 복사하고 재해시한다. SHA 불일치이면 xvlog/xsim 전에 중단한다.
TB는 `h1_verified.txt`의 신원 기록, blob 크기/header, 각 입력의 정확한 byte 수, golden 384개 비-X를 추가 확인한다.
SHA 계산은 SystemVerilog가 아닌 Python host에서 한다. 종료 뒤 staged 파일의 SHA도 다시 확인한다.
단독으로 xsim을 임의의 staged 파일에 실행하면 H1 절차를 만족하지 않는다. 보고서와 함께 보존한 runner를 사용한다.

## H2/H3 실행

`pose_cnn` + 실물 M00 + AXI 메모리 모형. CSR 입력은 TB가 구동한다.
BASE=0x10000000 / INPUT=0x20000000 / OUTPUT=0x30000000, 메모리 모형 기본 stall/latency 조건.
공통 reset → 실제 LOAD 1회 → 현재 입력 INFER → 같은 입력 INFER → zero 입력 INFER 순서다.
세 INFER 사이에는 reset/LOAD를 넣지 않으므로 동일 모델의 연속 실행도 검증한다.
입력 RAM의 모든 1,440회 write 주소·64-bit 값을 원본 입력 binary와 대조한다.
Encoder 시간은 enc_start가 수락된 상승 에지에서 enc_done이 관측된 상승 에지까지 경과 cycle이다.

## H4 포트 수집

enc_done 관측 후 다음 하강 에지부터 flat 주소를 0..383 순서로 공급한다.
각 주소 다음 상승 에지의 NBA 갱신 후 `#1`에 **실제 flat_rdata 포트**를 읽는다.
Pool RAM 내부 배열이나 Pool write 버스를 기대값으로 쓰지 않는다. golden_current의 파일이 유일한 수치 기준이다.
같은 word 안의 byte 비교는 `[8*b +: 8]`로 하며 word→좌표는:

```text
rx = word / 128
oc = (word % 128) / 4
oh = 2*(word % 4) + byte_lane/4
ow = byte_lane%4
```

각 실행의 384 word를 `rtl_flat_run0/1/2.hex`에 저장하고, 전체 1,152 word 비교를 `flat_all_words.csv`에 기록한다.
불일치 word/byte 개수, 첫 5개 값, rx/oc/oh별 byte 분포를 출력한다. X도 불일치다.

## H5 원인 분리

실행 중에는 주소를 건드리지 않고 다음을 관측한다:

- ENC에서 D09 두 선택 신호가 0인지, Encoder에 도달한 pool_mult/shift가 header와 같은지.
- Param/LUT 주소의 알려진 raw 범위와 유효 요청 범위를 따로 센다. 유효 시점은 기존 E/X-02a와 동일하게 acc_valid / GELU rq_valid_r0다.
- 알려진 Conv/Param/LUT 주소를 상승 에지 직전에 저장하고, 동기 RAM의 다음 출력이 blob 독립 주소식과 맞는지 전 cycle 비교한다.

H4 불일치가 있으면 세 INFER가 모두 끝난 **idle에서만** Loader의 Conv/ENC Param/ENC LUT/FCW read 주소를 임시 force한다.
write·state·data는 force하지 않는다. 선택 신호는 Top의 실제 idle=Encoder 선택을 그대로 사용한다.
각 RAM의 출력 포트로 333×16=5,328 Conv byte / 328×3=984 Param field / LUT 1,024 byte / FCW 2,432 word를 전량 읽는다.
기대값은 blob에서 `/`와 `%`를 써 독립 계산하며, 내부 저장소 계층 참조는 하지 않는다. 종료 후 주소 force를 release한다.

RAM 내용부터 틀리면 Loader/배선 원인을 조사해야 한다. RAM 전량과 실행 중 응답·입력·선택·pool 전달이 모두 맞는데
flat이 다르면 Encoder 연산 경로의 수치 불일치라는 근거가 된다. 구체적인 연산/파이프라인 수정은 이번 단계에서 하지 않는다.

## 판정과 회귀

runner는 xsim exit=0만으로 통과시키지 않는다. `RESULT: G-02 COMPLETE cases=3`와 `$finish`, fatal/제어 FAIL 부재를 확인한다.
**H4_pass=0이어도 관측 절차는 완료될 수 있다. 이를 Encoder 통과로 표시하지 않는다.**
기존 21 TB는 각각 별도 PASS/finish 및 오류·경고 부재를 확인하고 이전 관측 출력과 대조한다.
합성은 하지 않는다. 마지막으로 기존 파일 전체 SHA와 파일 집합을 작업 전과 대조한다.
