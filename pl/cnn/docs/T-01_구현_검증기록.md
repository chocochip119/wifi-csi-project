## 3. 핵심 신호·상태와 동작

`state_reg/state_next`는 현재/다음 상태다. 상태는 2비트 `IDLE=00`, `BUSY=01`이며, `status_busy`는 현재 상태가 BUSY인지로 결정한다. 상태와 설정은 상승 에지에서 `<=`로 저장하고 조합 블록은 `always @(*)`와 `=`를 사용한다.

`cmd_reg/input_addr_reg/weight_addr_reg/output_addr_reg`는 수락한 실행의 32비트 unsigned snapshot이다. START 이후 CSR 값이 바뀌어도 이 네 값은 다음 수락 START나 reset까지 보존된다. 오류 판정은 이전 `cmd_reg`가 아니라 **그 에지에 snapshot하는 `reg_cmd`와 당시 `cfg_ok`**를 사용한다.

`run_error_reg`는 내부 결과, `done_reg/error_reg`는 PS 표시다. 결과는 CMD가 0/1 외이면 BAD_CMD=1, CMD=0이면서 cfg_ok=0이면 NO_CFG=2, 그 밖이면 0이다. LOAD에는 cfg_ok가 필요하지 않다.

| 상승 에지 | 하는 일 | 에지 직후 표시 |
| --- | --- | --- |
| E0: CSR가 START 쓰기를 commit | CSR가 `reg_start=1`을 출력 | ctrl은 아직 IDLE, 이전 표시 유지 |
| E1: ctrl이 START 수락 | 설정 snapshot, 내부 결과 판정, 이전 done/error 해제 | busy=1, done=0, error=0 |
| E2: BUSY 종료 | 저장한 결과를 표시하고 IDLE로 복귀 | 성공: busy=0/done=1/error=0, 오류: busy=0/done=0/error=1 또는 2 |

따라서 **해제는 START 수락 에지(E1), 기록은 종료 에지(E2)**에 일어난다. 새 오류가 이전 표시 해제에 덮이지 않고, 오류도 busy를 정확히 한 클록 유지한다.

CLEAR는 표시만 지운다. 내부 결과나 snapshot·실행 상태에는 대입하지 않는다. 조합 블록에서 CLEAR를 먼저 처리하고 BUSY 종료 결과를 나중에 대입하므로 같은 에지에는 결과가 이긴다. 현재 BUSY는 한 클록뿐이어서 BUSY 중 CLEAR 검사는 곧 종료 에지 경합 검사다. 표시가 이미 0인 구간이며, CLEAR 때문에 종료 결과가 사라지지 않는 것을 확인했다. 여러 클록 실행에서 중간 CLEAR 후 최종 결과 재표시는 후속 실행 경로에서 추가 확인할 대상이다.

BUSY에서 START는 snapshot을 바꾸거나 새 실행을 만들지 않는다. 종료 에지에 들어온 START도 무시한다. 아직 외부 완료/오류 이벤트를 소비하지 않으므로, 복수 메모리/계산 오류의 중재나 drain을 검증한 것으로 해석하지 않는다.

reset은 `posedge clk or negedge rst_n`으로 비동기 assert한다. 동기 release는 상위 공통 reset 경계의 책임이며 이 모듈에 별도 동기화기를 넣지 않았다.

## 4. 실행한 확인과 결과

환경: Vivado xsim 2020.2. RTL 2개는 `xvlog`, TB 6개는 `xvlog -sv`, 각 top은 `xelab` 및 `xsim -runall -onerror quit`로 실행했다. 전부 첫 실행에서 통과했다. 각 TB의 최종 PASS 문자열과 종료 결과를 확인했다.

| TB | 실제 결과 |
| --- | --- |
| `tb_ctrl_status` | PASS. START snapshot 12회(중간 reset으로 취소한 1회 포함), 사용하지 않는 출력 66클록 0 유지 |
| `tb_csr_ctrl_link` | PASS(도달 가능한 조건). START 7회, busy 총 7클록, AXI busy snapshot 6회, busy COMMAND commit 0회 |
| `tb_s00_axi_write` | PASS. 기존 파일 그대로, AW/W/commit/B 각 5회 |
| `tb_s00_axi_regs` | PASS. 기존 파일 그대로, 쓰기/commit/B 각 49회 |
| `tb_s00_axi_read` | PASS. 기존 파일 그대로, AR/R 각 50회, write commit/B 각 7회 |
| `tb_s00_axi_ctrl` | PASS. 기존 파일 그대로, BUSY 1/2/8클록 모형, busy RW 거부와 값 보존, 경계 START 검사 |

단독 TB는 LOAD, INFER(cfg=0/1), CMD=2/FFFFFFFF/80000000, sticky 표시, 새 START의 이전 done/error 해제, 연속 오류, IDLE/BUSY CLEAR, START+CLEAR, BUSY START 무시, 네 설정값 보존, START 후 cfg 변경 무시, 실행 중 비동기 reset을 확인했다. 사용하지 않는 입력들을 변경하면서 출력이 계속 0인지도 검사했다.

정적 검토: 모든 `*_next` 8개에 조합 시작 기본값이 있고, case의 불법 상태 복구가 있다. 직접 설계 RTL에 `for/task/function/initial`, 지연, 내부 tri-state, RAM 전체 reset을 추가하지 않았다. **코드 검토상 래치 유발 대입 누락은 없으며, 합성에 의한 래치·자원·타이밍 확인은 하지 않았다.**

AXI 통합에서 관측한 PS 시퀀스:

| 설정 및 요청 | 실제 STATUS 읽기 순서 | 의미 |
| --- | --- | --- |
| cfg=0, COMMAND=1 → START | `0x01 → 0x02` | busy → done |
| CLEAR | `0x00` | done/error 해제 |
| cfg=0, COMMAND=2 → START | `0x01 → 0x14` | busy → BAD_CMD |
| cfg=0, COMMAND=0 → START | `0x01 → 0x24` | busy → NO_CFG |
| CLEAR 없이 같은 실패 재시작 | `0x01 → 0x24` | 이전 error 해제 → 새 NO_CFG |
| cfg=1, COMMAND=0 → START | `0x09 → 0x0A` | cfg 유지, busy → done |
| idle START+CLEAR | `0x09 → 0x0A` | 같은 실행 규칙 유지 |

종료 조건은 `busy==0 && (done || error)`이며 TB watchdog과 폴링 횟수 제한이 있다. 읽기는 AR 수락 에지의 갱신 전 값을 저장하므로, E2에 수락한 STATUS 읽기로 1클록 busy를 관측했다. 실제 PS가 이 짧은 busy를 반드시 볼 필요는 없다.

## 5. 명세 완료 조건 14의 도달 불가능한 항목

**실제 CSR+T-01 ctrl에서 “busy 중 COMMAND commit → SLVERR·값 보존”은 확인하지 못했다.** 현재 구조로는 그 commit 자체를 만들 수 없다. 이를 통과로 표시하지 않는다.

| 에지 | CSR 쓰기 경로 | ctrl 상태(에지 전 → 후) |
| --- | --- | --- |
| E0 | START commit, BVALID·reg_start 발생 | IDLE → IDLE |
| E1 | 가장 빠른 START B handshake. 이 에지도 새 AW/W 수락 불가 | IDLE → BUSY |
| E2 | 가장 빠른 다음 COMMAND AW/W 수락 | BUSY → IDLE |
| E3 | 다음 COMMAND commit | IDLE → IDLE |

통합 TB는 BUSY가 1인 구간에 후속 COMMAND를 내보내고 E3에서 OKAY와 값 갱신을 확인했다. `command_commit_cycle - start_commit_cycle == 3`을 검사했다. 완료된 실행 snapshot은 이전 CMD=1을 그대로 유지했다.

이 결과는 PROJECT_CONTEXT 5.1 D03 R2-1의 **거부 판단은 commit 당시 busy를 본다**는 계약과 일치한다. SLVERR를 만들기 위해 busy를 강제로 연장하거나 내부 신호를 force하지 않았다.

현재 CSR의 busy 거부·값 보존은 수정하지 않은 `tb_s00_axi_ctrl`의 수동 busy 모형 검사로 통과했다. **검수 제안:** 원래 완료 조건 14의 마지막 항목은 실제 LOAD가 여러 클록 실행되는 T-02 이후의 통합 검사로 이월한다. 이는 제안이며 다음 단계 구현 승인이나 팀 결정으로 기록하지 않는다.

## 6. 아직 동작하지 않는 범위·남은 결정

- DDR read/write 발행, mem 데이터 전달·backpressure, 마지막 B 응답 대기.
- Loader/Encoder/FC 시작·완료 순서, 입력 버퍼 쓰기, FIFO 공급, pose 출력.
- error 3/4/5, 오류 drain, cfg_ok 무효화, FIFO 복구, D08 관련 abort 신호.
- 실제 LOAD/INFER, 코어 wrapper 연결, 합성, 보드 실행.

미사용 출력 19개는 0에 고정했으며, 후속 포트 입력은 이번 상태 전이에 사용하지 않는다. Loader abort 포트 가능성은 D08-1 주석만 남겼다. D06–D10 결정 상태와 공통 인터페이스는 변경하지 않았다. 다음 후보 제목은 **T-02: mem read 발행과 LOAD 순서(M00·Loader 모형)**다.
