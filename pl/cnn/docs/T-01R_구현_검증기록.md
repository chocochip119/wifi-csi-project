# T-01R — Top FSM 13상태 골격과 IDLE / DECODE / FINISH

날짜: 2026-09-25. 상태: 구현·RTL 시뮬레이션·단독 합성 완료 / Claude 검수·사용자 확인 대기.

T-00 목표 도면의 13상태 골격에 START 수락, 명령 판정, 결과 표시를 옮겼다.
**이번 코드는 부분 구현이다. LOAD/INFER의 실제 전송·연산은 수행하지 않으며,
유효한 명령도 DECODE → FINISH를 거쳐 임시 성공으로 종료한다.**
메모리·Loader·Encoder·FC 제어 출력 19개는 모두 0이다.

## 2. 도면과 상태 인코딩 대조

도면 XML의 `fsm_code_*` 13개와 RTL의 `localparam [3:0]` 값을 직접 비교해
**13/13 일치**를 확인했다. TB에서도 상태 상수와 state_reg/state_next의 4-bit 폭을 검사했다.

| 상태 | 도면 | RTL | 이번 동작 |
| --- | --- | --- | --- |
| IDLE | 0000 | 0000 | START 수락 및 snapshot |
| DECODE | 0001 | 0001 | 저장한 cmd와 현재 cfg_ok 판정 |
| LD_RD1 | 0010 | 0010 | 미구현: IDLE 복구 |
| LD_RD2 | 0011 | 0011 | 미구현: IDLE 복구 |
| LD_WAIT | 0100 | 0100 | 미구현: IDLE 복구 |
| IN_RD | 0101 | 0101 | 미구현: IDLE 복구 |
| ENC | 0110 | 0110 | 미구현: IDLE 복구 |
| FC1 | 0111 | 0111 | 미구현: IDLE 복구 |
| FC2 | 1000 | 1000 | 미구현: IDLE 복구 |
| FC3 | 1001 | 1001 | 미구현: IDLE 복구 |
| WR | 1010 | 1010 | 미구현: IDLE 복구 |
| ERR_DRAIN | 1011 | 1011 | 미구현: IDLE 복구 |
| FINISH | 1100 | 1100 | 출구 에지에서 결과 기록 |

도면 전체의 20개 전이를 구현한 것은 아니다. 정상 LOAD의 LD_RD1 목적지는 T-03,
정상 INFER의 IN_RD 목적지는 T-04에 연결하며, 이번에는 두 경로 모두 FINISH로 간다.
미구현 10상태와 불법 인코딩 13~15는 상태만 IDLE로 복구한다. 내부 결과·표시·snapshot을
임의로 바꾸지 않으며, 독립적인 CLEAR 이벤트는 표시 해제 규칙대로 처리한다.

## 3. 동작과 기존 T-01에서 달라진 점

### START → 판정 → 결과 기록

| 상승 에지 | 에지 전 상태 | 에지에서 하는 일 | 에지 후 상태 / busy |
| --- | --- | --- | --- |
| A | IDLE, reg_start=1 | cmd/input/weight/output snapshot, run_error=0, 표시 해제 | DECODE / 1 |
| B | DECODE | cmd_reg와 이때의 cfg_ok로 판정, 내부 결과 저장 | FINISH / 1 |
| C | FINISH | 내부 결과를 done/error에 기록 | IDLE / 0 |

busy는 `(state_reg != IDLE)`이고, START 수락 직후부터 정확히 2cycle이다.
START는 IDLE에서만 수락한다. DECODE와 FINISH의 START는 snapshot이나 결과를 바꾸지 않는다.

이전에는 START 에지에 들어오는 `reg_cmd`와 `cfg_ok`를 판정했다.
이제 START에서 `reg_cmd`를 저장한 뒤 **DECODE에서 이번 요청의 cmd_reg**를 사용한다.
따라서 직전 요청의 명령을 잘못 쓰지 않으며, START 이후 입력 reg_cmd/주소 변화도 영향을 주지 않는다.
`cfg_ok`는 snapshot하지 않고 DECODE를 떠나는 에지의 값을 사용한다.

- INFER: START에서 cfg=0, DECODE에서 cfg=1이면 성공.
- INFER: START에서 cfg=1, DECODE에서 cfg=0이면 NO_CFG(2).
- FINISH에 들어간 뒤 cfg가 바뀌어도 이미 저장한 결과는 유지.
- LOAD는 cfg와 무관하게 성공 자리로 분기. 그 외 명령은 BAD_CMD(1).

### D02 / D03 및 reset

`run_error_reg`는 내부 실행 결과, `error_reg`는 소프트웨어 표시이며 기존 분리 구조를 유지했다.
수락한 START는 표시를 지우고(R1), CLEAR는 표시만 지운다(R3).
FINISH 출구에서 새 결과를 기록하며(R2), 조합 코드에서 CLEAR보다 나중에 기록하므로
같은 에지에서는 기록이 우선한다(R4). START 해제와 FINISH 기록은 서로 다른 에지다.

Top만 `always @(posedge clk)` / `if (!rst_n)`의 동기식 active-low reset으로 바꿨다.
TB는 FINISH 도중 reset을 내려도 에지 전에는 상태가 유지되고, 다음 상승 에지에
상태·snapshot·내부 결과·표시가 모두 초기화되며 가짜 완료가 생기지 않는지 확인했다.
S00/M00의 기존 reset 구현은 이번 범위에서 변경하지 않았다.

### 실제 CSR 경계의 변화

CSR START commit을 E0라고 하면 E1에 Top이 START를 받아 DECODE로 들어간다.
가장 빠른 후속 AW/W 수락은 E2이고, COMMAND commit은 E3이다.
E3에서 Top은 FINISH를 떠나지만 CSR은 **에지 전 busy=1**을 보므로 SLVERR를 저장한다.
이전 1cycle busy에서의 OKAY 기대값을 SLVERR로 바꾸고 COMMAND=1 보존을 검사했다.
거부 응답은 Top이 IDLE로 돌아간 뒤에도 그대로 유지된다.

## 4. 실제 검증 결과

Vivado 2020.2. RTL은 `xvlog`, TB는 `xvlog -sv`로 컴파일했다.
기존 CSR TB는 소스 수정 없이 실행했다.

| 대상 | 실제 결과 |
| --- | --- |
| tb_s00_axi_write | PASS: AW=5, W=5, commit=5, B=5 |
| tb_s00_axi_regs | PASS: writes=49, commit=49, B=49 |
| tb_s00_axi_read | PASS: AR=50, R=50, commit=7, B=7 |
| tb_s00_axi_ctrl | PASS: N=1/2/8 및 15a/15b/15c busy 경계 포함 |
| tb_ctrl_status | PASS: START snapshot 14회, 미구현 10+불법 3상태 복구, 출력 0 검사 104cycle |
| tb_csr_ctrl_link | PASS: START=7, busy=14cycle, AXI busy 읽기=6, busy COMMAND commit=1 |

단독 TB에는 LOAD/INFER 성공, NO_CFG, 32-bit BAD_CMD 3종, sticky 표시,
IDLE CLEAR, 새 START 해제, START+CLEAR, DECODE/FINISH의 START 무시·CLEAR,
FINISH 기록 우선, cfg 전환 양방향, snapshot 보존, reset 검사가 포함된다.
복구 검사는 BAD_CMD가 내부와 표시에 남은 상태에서 주입하므로, 잘못된 결과 초기화도 잡는다.

최초 6TB는 모두 PASS였다. 단독 TB의 force RHS가 task 인자라 xelab에서
`XSIM 43-4328` 경고가 1건 발생했다. module-level reg로 옮기고 실제 주입값 검사도 추가한 뒤
**영향받은 단독 TB만 재실행하여 경고 없이 PASS**를 확인했다. RTL은 이때 변경하지 않았다.
최초 실행과 재검사 출력 모두 부록과 로그에 보존했다.

정적 확인: 13상태 XML/RTL 일치, state 폭, 동기 reset sensitivity,
직접 설계 RTL의 for/task/function/initial/지연 미사용, 보호 파일 SHA-256 일치.
조합 블록의 모든 next 신호에는 기본 대입이 있고, 실제 합성에서도 래치 0을 확인했다.

## 5. 합성 점검 1회

사용자가 지정한 명령을 `cnn_rtl/syn`에서 실행했다.

```text
vivado -mode batch -source syn_check.tcl -nojournal -nolog -tclargs pose_cnn_ctrl xc7z010clg400-1 ../rtl/pose_cnn_ctrl.v
```

설치 경로의 `C:\Xilinx\Vivado\2020.2\bin\vivado.bat`를 직접 호출한 것 외에
스크립트·인자·XDC는 변경하지 않았다.

| LUT | FF | BRAM | DSP | Setup WNS | 래치 | 조합 루프 |
| ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| 19 | 40 | 0 | 0 | +4.885 ns | 0 | 0 |

대상은 xc7z010clg400-1, OOC, 잠정 100 MHz 및 입출력 지연 2 ns이다.
Setup failing endpoint는 0, 임계 경로는 상태 FF → status_busy다.
합성은 정상 종료했고 `SYN_CHECK_DONE`, exit code 0을 확인했다.

경고를 구분해 기록한다.

- `synth_design` 자체: 오류 0 / critical warning 0 / warning 0.
- 실행 시작의 `Common 17-741` CRITICAL WARNING: 로컬 Tcl store 경로 `C` 쓰기 권한 문제로 설치 경로를 사용한다는 환경 메시지. 실행은 계속되어 합성·보고를 완료했다.
- `Timing 38-242`: OOC clock port의 HD.CLK_SRC 미지정. 실제 clock buffer 위치·skew가 확정된 타이밍 결과가 아니다.
- `Vivado 12-180`: 래치 검색 결과가 비어 발생한 메시지. 실제 `LATCH count = 0`이다.

WNS는 **합성 단계 추정치**이며 배치·배선/hold/보드 타이밍 검증을 뜻하지 않는다.
이번에 도달 가능한 IDLE/DECODE/FINISH는 Vivado가 3-bit one-hot으로 재인코딩했고,
아직 소비처가 없는 주소 snapshot은 최적화됐다. 이는 부분 구현의 합성 결과이며,
RTL 인코딩·snapshot 동작 검증과 구분한다. 하드웨어 fault 복구를 검증한 것도 아니다.

## 6. 남은 범위와 Notion 복사용 요약

LD_RD1/LD_RD2/LD_WAIT/IN_RD/ENC/FC1/FC2/FC3/WR/ERR_DRAIN의 실제 동작,
메모리 명령·데이터 전송, 연산 start, 오류 코드 3/4/5는 미구현이다.
D06/D08/D09는 이번 단계에서 결정하지 않았다. S00/M00 reset 이행과 D07 공급 조건,
D10 보드·클록도 별도 항목으로 유지한다.

