# L-01 Blob Decoder 골격 구현·검증 기록

작성: 2026-09-26, Codex. 사용자 승인 범위 L-01만 구현했다. Claude 검수·사용자 확인 전이며 다음 단계 승인이나 Notion 기록 완료를 의미하지 않는다.

3,722 beat의 수락·11구간 판별·8/2/1 처리 주기·header 검사를 구현했다. 신규 TB의 완전 스트림 25회와 기존 15종 TB를 실제 실행해 통과했다. **명세에 적힌 합계 9,388은 산술 오류이며, 명세의 구간별 식을 합하면 9,772 cycle이다. RTL 실측도 9,772다.**

## 1. 구현 전에 정리한 명세 문제와 적용 범위

| 항목 | 적용한 해석·결정 |
|---|---|
| D2 총 cycle | 11구간·구간별 beat 수·8/2/1 규칙을 그대로 유지했다. 합계는 9,772이며 원문 9,388보다 384 크다. 숫자 9,388에 맞추려고 타이밍을 줄이지 않았다. |
| header 오류의 “즉시 종료” | 이어지는 상세 지시 및 D4에 따라 오류는 즉시 내부 보관하고, READY=1로 나머지를 버린 뒤 3,722번째 beat에서 done+err을 낸다. 중간에 READY=0으로 막거나 완료 펄스를 먼저 내지 않는다. |
| 3,722개 초과 검사 | **사용자 답변: “완료 전 추가 VALID 감지로 한정 (권장)”**. 마지막 정상 beat의 후속 처리 7 cycle 중 추가 `ld_valid`가 관측되면 길이 오류다. READY=0이므로 그 beat는 수락하지 않는다. 완료 이후 늦게 오는 입력은 이전 LOAD의 초과분인지 식별할 EOF가 없으므로 대상에서 제외한다. |
| version 기대값 | reference asset에는 2지만 RTL 계약 숫자는 미확정이다. `EXPECTED_VERSION=2`, **`CHECK_VERSION=0` 기본값**으로 두었다. 켠 경우 불일치 오류, 끈 경우 무시를 각각 검증했다. 통합 전에 version=2를 확정하고 검사를 켜는 것을 권장한다. |

## 3. 신호와 동작

`IDLE → RECEIVE ↔ WORK → IDLE`이 정상 경로다. RECEIVE에서 `ld_valid && ld_ready`가 성립할 때만 beat를 받는다. 64-bit 데이터와 처리 구간을 저장하고 수락 개수를 1 증가시킨다. 외부 공급이 멈추면 개수는 유지된다.

- header/FCW: 수락 에지에서 1회 처리가 끝난 것으로 간주해 READY를 계속 1로 둔다.
- Param: 수락 에지 1회 + WORK 1 cycle. READY=0은 1 cycle이다.
- Conv/LUT: 수락 에지 1회 + WORK 7 cycle. READY=0은 7 cycle이다.
- idle에서는 READY=0이다. busy 중 START는 카운터·header·진행 상태를 초기화하지 않는다.

예를 들어 beat 4(Conv1 weight)를 받으면 데이터를 보관하고 7 cycle 동안 READY=0을 유지한 뒤 beat 5를 받는다. 마지막 beat 3,721도 LUT 처리 8회를 모두 마친 에지에 `loader_done=1`이 된다. START 수락을 cycle 0으로 보면 첫 beat는 1, 마지막 수락은 9,765, 완료는 9,772다.

`beat_count_reg`는 수락 **개수**다. 수락 직전 0~3,721은 해당 beat의 인덱스이고, 마지막 수락 후 3,722는 종료 개수다. 인덱스 3,722인 beat를 수락하거나 RAM 주소로 쓰지 않는다. `region_code`와 `region_writes`는 포트를 추가하지 않은 내부 관측 신호이며, TB가 계층 참조로 모든 beat와 경계를 확인한다. WORK에서 사용할 데이터와 구간은 별도 보관한다.

header 오류는 `error_reg`에 보관하고 `DRAIN`에서 READY=1로 남은 스트림을 받는다. 실제 RAM 쓰기를 하지 않으므로 drain의 각 beat는 1 cycle이다. 최종 beat에서 done=1/err=1/cfg=0을 함께 내고 idle로 돌아간다. 성공이면 done=1/err=0/cfg=1이다. done/err는 1 cycle이며 cfg는 다음 수락 START 또는 reset까지 유지된다. START에서 header 출력 레지스터도 0으로 초기화한다.

**이번 cfg_ok=1은 L-01의 전체 스트림/header 검사 성공을 뜻한다. 상주 RAM은 아직 쓰이지 않는다.** Top에 실물 Loader로 연결하지 않았으며 기존 `loader_stub`도 그대로다.

## 4. beat 지도 및 READY 관측

원문 `09_Loader_주소맵`의 word `[0,1484)`와 `[99788,105748)`을 순서대로 받는다. 각각 742/2,980 beat로 합계 3,722다. 중간 FC1 weight 영역은 이 LOAD 스트림에 없다. beat 742에서 별도 재시작하지 않는다.

다음은 연속 정상 입력 case 0의 **계산값과 실측이 모두 같은 값**이다. cycle은 수락 에지와 후속 WORK를 합한 처리 시간이며 공급 공백은 제외한다.

| 구간 코드 | 내용 | beat 범위 | beat 수 | 처리/beat | 처리 cycle | READY=0 cycle |
|---:|---|---|---:|---:|---:|---:|
| 0 | header | 0~3 | 4 | 1 | 4 | 0 |
| 1 | Conv1 weight | 4~93 | 90 | 8 | 720 | 630 |
| 2 | Conv1 param | 94~117 | 24 | 2 | 48 | 24 |
| 3 | Conv2 weight | 118~693 | 576 | 8 | 4,608 | 4,032 |
| 4 | Conv2 param | 694~741 | 48 | 2 | 96 | 48 |
| 5 | FC1 param | 742~933 | 192 | 2 | 384 | 192 |
| 6 | FC2 weight | 934~2981 | 2,048 | 1 | 2,048 | 0 |
| 7 | FC2 param | 2982~3173 | 192 | 2 | 384 | 192 |
| 8 | FC3 weight | 3174~3557 | 384 | 1 | 384 | 0 |
| 9 | FC3 param | 3558~3593 | 36 | 2 | 72 | 36 |
| 10 | GELU LUT | 3594~3721 | 128 | 8 | 1,024 | 896 |
| **합계** | | | **3,722** | | **9,772** | **6,050** |

`4+720+48+4608+96+384+2048+384+384+72+1024 = 9772`.
100 MHz에서는 공급 공백 없는 Loader 단독 97.72 μs다. DDR/M00 지연이나 Top 전체 LOAD 시간을 포함한 수치가 아니다.

## 5. header 기대값 근거

| parameter | 기본값 | 검사 |
|---|---:|---|
| EXPECTED_MAGIC | 0x36574C50 | 항상 |
| EXPECTED_VERSION | 2 | CHECK_VERSION=1일 때만, 기본 0 |
| EXPECTED_TOTAL_WORDS | 105,748 | 항상 |

근거는 [full_pose.h 25행](D:/2609_final_project/wifi-csi-pose-main/HLS/pl_accel_v6/full_pose.h:25)의 `WEIGHT_MAGIC`, 26행 `WEIGHT_VERSION`, 27행 `WEIGHT_WORDS`와 422,992-byte 실제 reference blob이다. 명세가 언급한 공통 문서 8절 대신 숫자를 직접 가진 원본으로 대조했다. bin을 새로 생성하거나 수정하지 않았다.

실제 blob 첫 8 word를 little-endian uint32로 읽은 값:

```text
word0 magic        36574c50
word1 version      00000002
word2 total_words  00019d14   (105748)
word3 input_scale  3cb76adb   (미사용)
word4 output_scale 3bd997a8
word5 pool_mult    783b66b4
word6 pool_shift   0000001f   (31)
word7 reserved     00000000   (무시)
```

beat 하위 32-bit를 짝수 word, 상위 32-bit를 홀수 word로 처리한다. pool_shift는 32-bit signed로 비교한다. 정상 TB의 word4/5/6은 각각 위 값과 비트 단위로 일치했다. 기본 version 검사 제외는 계약 미확정의 임시 정책이며, version 불일치를 정상으로 받는 한계가 의도적으로 남아 있다. 전체 blob 데이터를 해석한 golden 검증은 이번 시험이 아니다. TB는 header와 결정적 패턴의 3,722 beat 스트림을 검증한다.

## 10. 검수 인계와 남은 범위

- L-01 RTL/TB 구현과 위 최소 검증을 마쳤다. 원문 합계 보정, version 기본 검사 제외, 사용자가 승인한 초과 VALID 감지 범위를 검수에서 확인할 수 있게 남겼다.
- 직접 설계 RTL에 for/task/function/initial/generate/genvar가 없다. reset sensitivity는 posedge clk뿐이며 현재값/다음값을 분리했다.
- L-02의 Conv/Param/LUT/FCW 실제 쓰기·상주 RAM, 배열별 shift 검사, D09 읽기 mux, X-02 Top 실물 연결은 구현하지 않았다.
- 이 단계의 DRAIN은 Loader header 오류 시 스트림을 끝까지 받는 내부 상태다. 이미 완성된 Top ERR_DRAIN 및 D08 정책은 수정하지 않았다.
