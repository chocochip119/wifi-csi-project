# T-07 구현·검증 기록 — ERR_DRAIN / D08

2026-09-26. 사용자 확정 D08(공통 문서 5.4절)을 적용했다. **Top FSM 13상태 구현 및 이번 단계 자체 검증 완료. Claude 검수와 사용자 확인은 별도다.** 실물 Loader/Encoder/FC 또는 BD 통합 완료를 뜻하지 않는다.

## 1. 구현 결과와 동작

`LD_RD1 / LD_RD2 / IN_RD / FC1`에서 `mem_rd_err`가 보이면 **그 cycle에** 소비 쓰기를 막고 `run_error_next=4`, `state_next=ERR_DRAIN`으로 정한다. 다음 edge에 ERR_DRAIN에 들어간다. `mem_rd_ready=1`로 남은 read를 버리고, **read와 write가 모두 idle일 때만** FINISH로 간다. FINISH를 떠나는 edge에 `done=0`, `error=4`를 공개한다.

M00의 `mem_rd_err`는 R 응답 수락 후 등록된다. 따라서 오류가 실린 beat 자체까지 이미 RAM/FIFO에 들어갈 수 있다. 이번 차단의 정확한 기준은 **Top이 mem_rd_err를 관측한 cycle부터**이며, RRESP가 붙은 beat를 사전에 거르는 기능을 추가한 것은 아니다. 입력 중간 오류에서 RAM 21 word, FC1 중간 오류에서 FIFO 1,285 word가 들어간 기존 관측값이 유지됐다.

ERR_DRAIN에서는 데이터도 0이다. `ld_valid/in_we/fifo_we=0`, `ld_data/in_wdata/fifo_wdata=0`, read/write/Loader/Encoder/FC START=0. 조합 블록의 기본값을 이용하므로 X 또는 don't-care가 없다. 이 상태는 내부 결과를 바꾸지 않는다.

WR은 변경하지 않았다. 마지막 B 응답까지 완료한 뒤 `MEM_WR_ERR=5`를 기록하고 FINISH로 직행한다. Top timeout, abort 포트, 강제 FC 중단, CSR 변경은 추가하지 않았다.

강제 조기 done은 실제 FC 완료 계약(모든 결과 기록 뒤 done)과 다른 제어 시험이다. 두 case에서는 TB 연결부만 FC2 START를 stub에 전달하지 않고, **DUT의 FC2 START/select 및 FC1 탈출을 관측한 후 FIFO의 49,152 pop까지 기다린다.** RTL force나 FC abort는 하지 않는다. 실제 FC가 idle이 되기 전에 다음 START를 넣어 가짜 정상 완료를 만들지 않는다. 해당 출력에는 `scope=FC1_boundary`, `done=0`이 찍힌다. 이를 전체 INFER 성공이라고 세지 않는다.

FC1 11조건/14회 관측을 모두 실행했다. D06의 서로 다른 두 base, 49,152 push/pop 전량 대조, overflow=0, full 실제 발생, done before/same/after/level을 보존했다. 대표값: 느린 소비 full=145,322 cycle·최대 연속 3, 난수 full=142,828·최대 37, 정지/재개 최대 연속 full=1,427. 정상 full INFER의 종결 기대 변경은 사용자 승인 작업 1 보정에 속하며, drain 때문에 정상 기능 기대를 바꾼 것은 아니다.

## 5. R4 동등성 비교

아래 cycle은 해당 START 수락 edge를 0으로 둔 TB 상승 edge 관측값이다. `read_fall`은 busy=0을 처음 샘플링한 cycle이다. 출력 전량은 [R4 CSV](T-07_R4_동등성.csv)에 있다.

|---|---:|---:|---:|---:|---:|
| LOAD RD1 중간 | 742 / 21 | 721→721 | 838→838 | 839→839 | 4 |
| LOAD RD2 중간 | 3,722 / 763 | 2,959→2,959 | 4,193→4,193 | 4,194→4,194 | 4 |

| 입력 마지막 | 1,440 / 1,440 | 0→0 | 1,622→1,622 | **1,623→1,624** | 4 |
| FC1 중간 | 49,152 / 1,285 | 47,867→47,867 | 58,571→58,571 | 58,572→58,572 | 4 |
| pose write BRESP | 입력/FC 데이터 전량 유지 | 0→0 | 56,925→56,925 | 56,959→56,959 | 5 |

**마지막 beat 오류의 Top 완료 +1 cycle은 의도한 상태 변경의 결과**다. 기존에는 mem_rd_err를 볼 때 busy도 이미 0이면 해당 상태에서 곧바로 FINISH로 갔다. 이제 반드시 ERR_DRAIN 1 cycle을 거친다. 정상 case, 실제 M00 완료 시점, 버리는 beat 수, 최종 done/error는 바뀌지 않았다.

FC1 오류 case의 `FC1_cycles`는 56,943→3,094로 줄고 ERR_DRAIN 53,849 cycle로 옮겨졌다. 합계 56,943은 동일하다. 상태별 계수의 정의가 달라진 결과이며 전송 시간이 짧아진 것이 아니다.

54쌍 중 error=0인 41개 관측(강제 FC1 경계 2개 포함)의 데이터·타이밍 값은 완전히 동일했다. 추가로 기존 T-06에 이미 저장된 정상 결과 28개(LOAD 5, 입력 11, full 12)의 **모든 보고 필드**도 그대로 대조해 일치했다([대조 기록](T-07_이전정상값대조.json)). 같은 새 TB를 두 번 돌린 비교에만 의존하지 않았다.

## 6. R5 RD_FAULT와 D08 복구 계약

| RLAST 주입 | fault 진입 전 R/RAM word | 관측 시간 | Top / M00 state | busy / 표시 error / 내부 error | TB reset 이후 |
|---|---:|---:|---|---|---|
| early (mode1) | 31 / 31 | 2,000 cycle | 11 / 4(RD_FAULT) | 1 / **0** / 4 | LOAD → INFER 정상 |
| missing (mode2) | 32 / 32 | 2,000 cycle | 11 / 4(RD_FAULT) | 1 / **0** / 4 | LOAD → INFER 정상 |

두 번째 burst에 RLAST 오류를 넣었으므로 T-02d의 첫 burst 시험(15/16 beat)보다 앞서 16 beat가 더 수신됐다. Top은 READY=1을 유지하지만 M00 RD_FAULT 자체가 진행하지 않는다. FINISH에 도달하지 않아 표시 error=0이다. PS는 이 경우 error 표시를 기다리지 않고 busy 시간 초과로 판단해야 한다. Top timeout은 없다. 이론적 무한 시간을 시뮬레이션했다는 뜻은 아니며, 2,000 cycle 관측 및 M00 기존 자기 유지 동작과 일치한다.

미완 read가 남은 고착 중에는 `check_quiescent`를 호출하지 않았다. TB의 모든 endpoint를 함께 reset한 뒤에는 quiescent 검사와 재LOAD·재INFER를 수행했다. **실제 Zynq/AXI interconnect/DDR를 포함한 reset 범위와 PS 제어 절차의 안전성은 이번 결과로 보증하지 않으며 X-03에서 검증한다.**

확정 PS 정책(Top/CSR에 재요청 금지 latch 등을 새로 만들지 않음):

| 상황 | PS 동작 |
|---|---|
| BAD_CMD(1), NO_CFG(2) | 원인을 해결해 재요청, reset 불필요 |
| BLOB_ERR(3), MEM_RD_ERR(4), MEM_WR_ERR(5) | reset → 재LOAD → 재INFER |
| busy timeout, error=0 | X-03에서 검증한 reset 절차 |

입력/FC1/write 실행 오류 뒤 복구 시험은 이 정책대로 공통 reset과 재LOAD를 명시한다. 정상 연속 INFER는 reset 없이 두 번 실행하는 기존 조건을 유지했다. RESET은 모든 TB endpoint에 동기식 active-low로 세 상승 edge 이상 걸치며, stub을 몰래 완료시키거나 FC를 자동 복구시키지 않는다.

## 7. 합성 1회

`xc7z020clg400-1`, 기존 100 MHz OOC 제약과 `syn_check.tcl` 사용. 구현/P&R은 하지 않았다.

| 항목 | T-06 | T-07 | 변화 |
|---|---:|---:|---:|
| LUT | 471 | **457** | −14 |
| FF | 220 | **225** | +5 |
| BRAM / DSP | 0 / 0 | 0 / 0 | 동일 |
| WNS | +1.728 ns | **+1.741 ns** | +0.013 ns |
| 래치 / 조합 루프 | 0 / 0 | 0 / 0 | 동일 |

setup failing endpoint=0, TNS=0. 임계 경로 `cmd_reg_reg[30]/C → mem_rd_bytes[11]`, 데이터 지연 5.251 ns, 4 LUT level. 동률 경로는 `mem_rd_start`이고 다음 경로는 `mem_rd_addr[0]`다. 1.0 ns 중단 기준에 걸리지 않았다.

**시뮬레이션의 xvlog / xvlog -sv / xelab 오류·경고는 최종 실행 0이다.** 합성 실행 전체에는 이전 단계와 같은 환경/제약 메시지 3건이 있다: `Common 17-741`(Tcl store 권한, critical warning), `Timing 38-242`(OOC HD.CLK_SRC 미지정), `Vivado 12-180`(래치 검색 결과 없음). 이를 숨기거나 합성 전체 경고 0이라고 표시하지 않았다. 합성 본체의 새 RTL 경고는 없고 latch/loop 검사는 0이다.

## 9. 검수 인계·남은 범위

T-07의 구현·자체 검증은 완료했다. 다음 단계 RTL/TB는 만들지 않았다. D09, 실물 Loader/Encoder/FC 결합, BD reset 검증은 후속 범위다.

## 10. Notion 복사용 요약

- T-07: ERR_DRAIN 구현으로 Top FSM 13상태 모두 구현. 검수·사용자 확인은 별도.
- LD_RD1/LD_RD2/IN_RD/FC1 오류 감지 cycle에 소비 쓰기 차단, 내부 error=4 저장 → ERR_DRAIN. READY=1로 버리고 read/write 모두 idle이면 FINISH.
- WR 오류는 기존대로 마지막 B 완료 후 error=5 → FINISH. CSR와 M00/S00·모형·stub은 변경하지 않음.
- 15종 TB 통과. LOAD 10 / 입력 13 / FC1 11 / full 13 case 모두 기본 실행. FC1 강제 조기 done 2건은 경계 시험으로 분리.
- T-06과 54개 관측쌍의 데이터·discard·M00 완료·최종 결과 동일. 정상 관측 41개 동일. 마지막 beat 오류 2건만 ERR_DRAIN 경유로 Top 완료 +1 cycle.
- RLAST early/missing 각각 2,000 cycle: Top busy=1, 표시 error=0, 내부 error=4. TB 공통 reset→LOAD→INFER 복구 확인. 실제 보드 reset 범위는 X-03.
- read/write 동시 drain: read 종료 뒤 write를 추가 4,386 cycle 기다림. 조기 FINISH 없음.
- 합성: LUT 457 / FF 225 / BRAM 0 / DSP 0, WNS +1.741 ns(T-06 대비 +0.013), 래치·조합 루프 0.
- PS 정책: 요청 거부 1/2는 원인 해결 후 재요청. 실행 오류 3/4/5는 reset→재LOAD→재INFER. busy timeout/error0은 검증된 reset 절차.
- Notion에는 아직 기록하지 않았으며 이 내용은 복사용 요약이다.
