# T-04 — INFER 입력 단계와 Encoder 구동

2026-09-25. **구현·자체 검증 완료, Claude 검수·사용자 확인 대기.** 이번 단계는 IN_RD/ENC까지다. ENC 완료 후 FINISH는 T-05 이전의 임시 종료이며, FC 연산이나 pose 출력까지 구현했다는 뜻이 아니다. Notion은 갱신하지 않았다.

## 1. 결과와 구현 전 확인

실물 M00_AXI와 기존 AXI 메모리 모형을 연결한 INFER 시험 **13조건·15회 모두 PASS**. 정상 입력은 RAM 주소 0~1439에 1,440 word가 정확히 한 번씩 기록됐다. 기존 **회귀 TB 12개**도 통과했다. 여기에는 tb_top_load 10조건 전부와 tb_m00_read_perf의 지연 0/16/32/64 전부를 포함한다.

기준은 사용자의 T-04 명세, [도면 ASM-INFER/공통](../doc/pose_cnn_ctrl_fsm.drawio), [PROJECT_CONTEXT.md](project_context/PROJECT_CONTEXT.md)다. 다음 사항을 구현 전에 알렸으며 인터페이스나 오류 정책을 임의로 변경하지 않았다.

1. 명세의 burst 범위 90~93은 현재 M00 알고리즘에서는 **정확히 90 또는 91**로 좁혀진다. 4 KiB 안의 8 B 정렬 시작 offset 512개를 독립 계산한 결과, 128 B 정렬 32개는 90 burst, 나머지 480개는 91 burst다. 처음 경계에서 짧게 나뉜 뒤에는 4 KiB=32×128 B에 맞춰 다시 정렬되므로 경계마다 추가 burst가 생기지 않는다. 실제 ARADDR/ARLEN도 TB가 독립 계산해 검증했다.
2. M00의 `mem_rd_err`는 RRESP 오류 beat를 수락한 edge 뒤에 등록된다. **오류 beat 자체는 이미 RAM에 기록될 수 있다.** Top은 err 관측 이후 쓰기를 막고 Encoder를 시작하지 않는다. 명세 N7의 “그 뒤로 0”을 이 시점으로 확인했다. M00나 공통 포트는 변경하지 않았다.
3. Encoder 지연 0은 START 수락 edge **직후** done을 내는 동기식 모형이다. 같은 edge에 Top도 ENC에 들어가므로 완료 펄스를 볼 수 있다. 임의의 비동기 sub-cycle 펄스는 시험 계약에 포함하지 않았다.

입력 RAM의 유효 주소는 0~1439다. 1440은 첫 범위 밖 주소로 검사한다.

기존 파일 수정 3개와 신규 TB 3개다. 보호 대상인 S00/M00/메모리 모형/loader_stub/Encoder 및 기존 LOAD·M00·모형·S00 TB는 그대로다. 사전 기록 31파일 중 **승인된 3파일만 변경**, 나머지 **28파일 해시 동일**. Top의 기존 **45포트 이름·방향·폭 동일**. [정적 검사·SHA-256](T-04_정적검사.json), [기존 3파일 변경분](T-04_changes.diff) 참조.

```text
IDLE → DECODE → IN_RD → ENC → FINISH → IDLE
                  └ 오류: 쓰기 중지·read drain → FINISH(error=4)
```

| 상태/전이 | 구현과 도면 대조 |
| --- | --- |
| DECODE → IN_RD | snapshot `input_addr_reg`, 11,520 B의 read START 1-cycle, beat=0. cmd snapshot과 DECODE cycle cfg_ok 판정 유지 |
| IN_RD 정상 등식 | busy=1, READY=1, in_we=mem_rd_valid, in_waddr=beat, in_wdata=mem_rd_data |
| IN_RD 판정 | **error → valid → busy 하강** 순서. valid인 정상 cycle에만 beat+1. VALID가 0이면 유지 |
| IN_RD → ENC | 이전 busy=1/현재 busy=0이고 valid=0일 때 enc_start=1. 실제 1,440 word 기록 후에만 발생 |
| IN_RD 오류 | 내부 결과 4, in_we=0, READY=1 유지. M00 busy=0 이후 FINISH. T-07에서 ERR_DRAIN으로 교체할 주석 유지 |
| ENC | busy=1, 나머지 출력 0. done 대기 후 FINISH. “T-05에서 FC1으로 교체, D06 필요” 주석 |
| FINISH | 떠나는 edge에 성공/오류 표시. D02의 실행 결과·표시 분리, CLEAR보다 기록 우선 유지 |

beat는 reset과 정상 INFER read 발행 때 0이 된다. 최종 write는 주소 1439이고 이후 카운터 값은 1440이지만 추가 write는 없다. RAM 내용 전체를 reset으로 지우는 RTL을 추가하지 않았다. 동기식 active-low reset 및 직접 설계 RTL의 for/task/function 금지 규칙을 유지했다.

13상태 4-bit localparam은 도면 XML과 직접 대조해 모두 일치했다.

```text
IDLE=0000 DECODE=0001 LD_RD1=0010 LD_RD2=0011 LD_WAIT=0100
IN_RD=0101 ENC=0110 FC1=0111 FC2=1000 FC3=1001
WR=1010 ERR_DRAIN=1011 FINISH=1100
```

미구현 FC1/FC2/FC3/WR/ERR_DRAIN 5상태와 불법 값 13/14/15는 결과·snapshot을 보존하면서 IDLE로 복구한다.

정렬 정상의 기본 길이는 `DECODE 1 + IN_RD 1621 + ENC(지연+1) + FINISH 1 = 1624+지연`이다. 동일 Encoder 지연 5에서 +8 비정렬은 burst 1개 증가로 입력에 2 cycle이 추가됐다. boundary_ff8_stalls에는 AR gap=7, R gap=2도 적용하므로 그 차이 전체를 주소 정렬 비용으로 해석하면 안 된다. [상세 결과 CSV](T-04_INFER_results.csv)

case 11의 두 실행 사이에는 hardware reset이 없다. 두 번째 START에서 beat를 다시 0으로 만들고, 이전 enc_done 레벨이 남아 있어도 새로운 Encoder START가 완료를 지운 뒤 설정 지연을 기다렸다. case 12는 중간 RRESP 오류 후 reset 없이 정상 입력을 다시 실행했다. 이전 read 오류가 다음 read START에서 지워지고 새 데이터 1,440 word를 모두 덮어썼다. 이는 **Encoder가 아직 시작되지 않은 입력 RRESP 오류의 시험 결과**이며 D08 전체 재시작 정책을 확정한 것이 아니다.

### Encoder의 0-cycle 완료

enc_start를 샘플링하는 edge에 Top은 IN_RD에서 ENC로 이동하고, stub은 같은 edge 직후 enc_done=1을 낸다. 이어지는 ENC cycle에서 완료를 보고 다음 edge에 FINISH로 간다. Loader처럼 완료가 관찰 상태 진입보다 먼저 사라지는 구조가 아니므로 별도 완료 보관 레지스터를 추가하지 않았다. 지연 0 + 1-cycle done 시험으로 확인했다. [상태 이벤트 CSV](T-04_infer_events.csv)

### 모형 자체 검사

in_ram_stub은 RAM과 별도로 written bit, write_count, 주소/값/cycle 로그를 보관한다. TB가 idle에서 `begin_transfer`로 관측 기록만 초기화하며 RAM 내용은 지우지 않는다. 실제 반복 추론에서는 같은 RAM 주소에 다시 쓰는 것이 정상이다.

임시 단위 TB에서 중복 주소, 주소 건너뜀, 주소 1440, X 데이터를 각각 넣어 **4/4 예상 fatal 검출**을 확인했다. enc_stub은 진행 중 새 START를 1회 기록하고 무시했으며, 원래 완료 지연 8-cycle과 설정 폭 2-cycle을 유지했다. 이 단위 시험의 의도한 Fatal과 긍정 통합 시험의 위반 0을 구분한다. [단위 시험 소스](T-04_stub_checker_source.txt) · [명령·출력 전문](T-04_stub_checks_run.txt)

## 4. 회귀 변경과 결과

상태/CSR TB의 짧은 모형은 데이터 연산 없이 read/Loader/Encoder handshake로 상태와 CSR 계약을 검사한다. 실물 M00와 입력 데이터의 전량 검증은 tb_top_infer가 맡는다. 기존 TB에서 INFER를 2-cycle 성공으로 보던 기대만 실제 IN_RD/ENC 경로에 맞췄고, 기존 오류·CLEAR·snapshot·cfg 관찰 시점 검사는 유지했다.

| TB | 수정 | 결과 |
| --- | --- | --- |
| tb_ctrl_status | 있음 | 14 START snapshot, D02/D03/reset, 미구현 5+불법 3상태 복구 PASS |
| tb_csr_ctrl_link | 있음 | START 7회, busy 50 cycle, busy 읽기 23회, busy COMMAND commit 거부 1회 PASS |
| tb_s00_axi_write/regs/read/ctrl | 없음 | 기존 4개 전체 PASS |
| tb_top_load | 없음 | CASE 0~9 전부 실행. T-03의 10개 PASS 관측 줄과 완전히 동일 |
| tb_m00_read | 없음 | 12/12, 전체 데이터·AR 범위 PASS |
| tb_m00_read_perf | 없음 | latency 0/16/32/64 모두 실행. cycles 55,296/104,448/153,600/251,904 유지 |
| tb_m00_write | 없음 | W1~W8 PASS |
| tb_m00_err | 없음 | E1~E9 22 case PASS, M00/C12 위반 0 |
| tb_axi4_slave_mem_model | 없음 | A/B/C/D PASS, 의도한 음성 시험 13건 검출 |

CSR 모형의 LOAD는 기존 12-cycle, INFER는 `DECODE 1 + IN_RD 4 + ENC 4 + FINISH 1 = 10 cycle`이다. 따라서 2 LOAD + 2 INFER + 3 즉시 오류의 busy 합계는 `24+20+6=50`이다. 이전 합계 34에서 INFER 2회의 증가분 16만 늘었다. START·busy 상태를 force로 늘리지 않았다.

회귀 TB는 총 12개, xsim 호출은 **21회**(기본 TB 11회 + LOAD CASE 10회)다. 모델 자체시험의 의도한 위반 13건은 M00 통합 위반과 별도다. xvlog/xvlog -sv/xelab 최종 오류·경고는 0이고, exit code와 함께 각 성공 표식 및 FAIL/Fatal 부재를 확인했다.
