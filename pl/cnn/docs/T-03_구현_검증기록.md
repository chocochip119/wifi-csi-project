# T-03 — Top FSM LOAD 경로 구현·검증

2026-09-25. **구현·자체 검증 완료, Claude 검수·사용자 확인 대기.** 승인 범위는 T-03이다. 실제 Loader, INFER 입력/Encoder, ERR_DRAIN은 구현하지 않았다. Notion은 갱신하지 않았으며 아래에 복사용 요약을 제공한다.

## 1. 결과와 적용 기준

`pose_cnn_ctrl → 실물 M00_AXI → AXI4 슬레이브 메모리 모형`, `pose_cnn_ctrl → Loader stub`을 연결해 LOAD를 확인했다. 통합 10조건과 회귀 TB 10개가 모두 통과했다. 완전한 LOAD에서는 **742 + 2,980 = 3,722개의 64-bit word를 전량 대조**했고, AR은 **47 + 187 = 234 burst**였다. 통합 시험의 AXI/C12/Loader 계약 위반은 0건이다.

기준은 [사용자 작업명세 원문](T-03_작업명세_원문.txt), [목표 도면](../doc/pose_cnn_ctrl_fsm.drawio), [공통 문서](project_context/PROJECT_CONTEXT.md)다. 원문의 다음 두 부분은 사용자가 후속 답변에서 승인한 보정을 적용했다.

| 항목 | 원문의 문제 | 사용자 승인과 반영 |
| --- | --- | --- |
| L7 오류 종료 | FINISH로 즉시 나가면 READY가 0이 되어 M00의 남은 R beat가 멈춤 | **“임시 drain 처리 허용 (권장)”**. 현재 LD_RD 상태에서 `ld_valid=0`, `mem_rd_ready=1`로 버리고, M00 busy가 내려간 뒤 FINISH |
| Loader 완료 관찰 | 마지막 beat 직후 done이 오면 아직 LD_RD2이므로 LD_WAIT에서 펄스를 놓침 | **“done/error 보관 추가 (권장)”**. LOAD 중 done과 같은 cycle의 error를 저장하고 LD_WAIT에서 판정 |

이는 T-03의 승인된 보정이며 D08 전체 결정은 아니다. 기존 도면 XML과 명세 원문은 수정하지 않았다. 도면의 정상 상태 등식은 유지하고 오류 처리 및 완료 펄스 보관의 차이를 이 기록에 명시한다.

기존 소스 중 수정은 위 3개 파일, 신규 소스는 TB 2개다. S00_AXI/M00_AXI/AXI 메모리 모형 및 기존 S00 4개·M00/모형 TB는 변경하지 않았다. Encoder도 변경하지 않았다. 사전 기록한 기존 15파일에서 승인된 3파일만 달라졌고 **나머지 12파일은 SHA-256 동일**하다. Top의 기존 **45포트 방향·폭도 동일**하다. [정적 검사·해시](T-03_정적검사.json), [기존 3파일 변경분](T-03_changes.diff) 참조.

정상 흐름은 다음과 같다.

```text
IDLE → DECODE → LD_RD1 → LD_RD2 → LD_WAIT → FINISH → IDLE
```

| 상태/전이 | 구현 | 도면과 대조 |
| --- | --- | --- |
| IDLE → DECODE | START 수락 때 command/주소 4개 snapshot, 내부 오류와 완료 보관 초기화 | D02 R1, D03 R1 유지 |
| DECODE → LD_RD1 | `loader_start=1`, `mem_rd_start=1`, snapshot base, 5,936 B | 같은 edge의 1-cycle 출력 |
| LD_RD1/LD_RD2 정상 | busy=1, `ld_valid=mem_rd_valid`, `ld_data=mem_rd_data`, `mem_rd_ready=ld_ready` | 정상 상태 등식 유지 |
| LD_RD1 정상 완료 | 이전 busy=1이고 현재 busy=0일 때만 두 번째 read: base+399,152, 23,840 B | 단순 `!busy`가 아닌 하강 검출 |
| LD_RD2 정상 완료 | busy 하강 후 LD_WAIT, 추가 read 없음 | 도면과 동일 |
| LD_RD1/LD_RD2 오류 | busy 하강 검사보다 오류를 먼저 판정. error=4 보관, Loader 전달 중지, READY=1, busy=0 후 FINISH | 사용자 승인 임시 drain. T-07 교체 주석 |
| LD_WAIT | busy=1로 대기. 현재 또는 저장한 done/error로 FINISH 선택. Loader 오류는 3 | 사용자 승인 완료 펄스 보관 |
| FINISH → IDLE | 성공 done=1/error=0, 실패 done=0/error=내부 결과 | 표시와 실행 결과 분리, 완료 기록이 CLEAR보다 우선 |

`CLEAR_STATUS`는 표시만 지우며 내부 실행 오류와 Loader 완료 보관을 지우지 않는다. 새 START 수락이 완료 보관을 초기화한다. INFER는 T-01R의 2-cycle 임시 종료 구조를 유지한다. 직접 작성 RTL에 `for`/`task`/`function`/`initial`을 추가하지 않았으며 동기식 active-low reset을 유지한다.

13상태의 RTL localparam은 도면 XML과 직접 대조했다.

```text
IDLE=0000   DECODE=0001  LD_RD1=0010  LD_RD2=0011  LD_WAIT=0100
IN_RD=0101  ENC=0110     FC1=0111     FC2=1000     FC3=1001
WR=1010     ERR_DRAIN=1011            FINISH=1100
```

미구현 7상태(IN_RD/ENC/FC1/FC2/FC3/WR/ERR_DRAIN)와 불법 값 13/14/15는 기존 결과와 snapshot을 보존하며 IDLE로 복귀한다.

## 3. L1~L9 검증 근거

| 항목 | 관측 및 판정 |
| --- | --- |
| L1 | 전 case에서 Loader START 1회. 정상 LOAD read START 2회, 각 1 cycle. 첫 Loader/read START 동시 수락. START 뒤 live command/weight 주소를 바꿔도 snapshot 주소 유지 |
| L2 | 정상 LD_RD cycle마다 3개 등식 검사. 항상 ready 조건 4,192회, 고정 8-cycle 조건 33,493회. 고정 stall 중 VALID 유지 29,301 cycle, ready 연속 LOW 최대 8. slave stall 혼합도 통과 |
| L3 | 구간1 마지막 742번째 beat 수락 뒤 busy 하강에서만 read #2. 주소/크기 검사 및 AR 범위 독립 계산으로 연속·무중복·전량 확인 |
| L4 | 구간2 busy 하강에서만 LD_WAIT 진입. 세 번째 read 없음 |
| L5 | done 지연에 따라 LD_WAIT 10/20/5/7 cycle 대기. 성공은 done=1/error=0, Loader 실패는 done=0/error=3. 즉시 done 및 즉시 done+error도 각각 정상 기록 |
| L6 | 두 상주 구간과 건너뛰는 구간을 서로 다른 seed로 채움. 정상·Loader 오류 7조건 모두 수집 배열 3,722 word 전량 일치. skipped FC1 패턴 유입 0 |
| L7 | 구간1/2 중간 RRESP 오류 후 해당 read의 남은 R을 모두 수락. error=4로 종료, LD_WAIT 체류 0. 추가 구간1 마지막 beat 오류도 오류 우선으로 처리하여 read #2 미발행 |
| L8 | 항상 ready 4,204 cycle, 각 beat 뒤 ready LOW 8-cycle 조건 33,505 cycle. 두 조건 모두 Loader 완료 지연 10-cycle로 동일. 정상 AR 47+187=234 |
| L9 | 수정한 ctrl/CSR 연결 TB 2개 + 수정하지 않은 S00 4개·M00 read/write/err·모형 자체시험 = 10개 PASS |

TB base는 `0x1C000000`이다. region1/skip/region2 seed는 각각 `AAAA0001`/`BBBB0002`/`CCCC0003`이며 주소에 따라 word가 달라진다. ARLEN도 TB가 남은 크기·16 beat·4 KiB 경계의 최소값으로 독립 계산한다. 오류로 Loader 전달이 중단된 case도 실제 전달된 모든 word를 온라인 대조한다.

Loader ready mode 2의 8/2/1 반복은 여러 처리 지연을 흉내 낸 패턴이며 실제 blob 구간 해석기는 아니다. mode 3은 seed `13572468`로 0~8 cycle을 선택한다. 모든 통합 case에서 `check_quiescent`를 호출했고 AXI/C12/Loader 계약 위반은 0건이었다. 통합 TB에 `expect_violation`을 사용하지 않았다.

### 10조건 측정표

cycle은 START 수락 edge부터 Top busy 하강 edge까지의 차이다. R은 M00가 받은 beat, Loader는 전달·대조한 word 수다.

| ---: | --- | ---: | --- | --- | ---: | --- |
| 0 | always_ready | 4,204 | 47 / 187 | 3722 / 3722 | 10 | 1 / 0 |
| 1 | fixed_8 | 33,505 | 47 / 187 | 3722 / 3722 | 10 | 1 / 0 |
| 2 | typed_and_slave_stall | 19,247 | 47 / 187 | 3722 / 3722 | 20 | 1 / 0 |
| 3 | random_and_slave_stall | 19,484 | 47 / 187 | 3722 / 3722 | 5 | 1 / 0 |
| 4 | blob_error | 4,201 | 47 / 187 | 3722 / 3722 | 7 | 0 / 3 |
| 5 | immediate_done | 4,195 | 47 / 187 | 3722 / 3722 | 1 | 1 / 0 |
| 6 | read_error_part1 | 839 | 47 / 0 | 742 / 21 | 0 | 0 / 4 |
| 7 | read_error_part2 | 4,194 | 47 / 187 | 3722 / 763 | 0 | 0 / 4 |

항상 ready와 고정 8-cycle 조건의 cycle 차이는 backpressure 관측값이며 실제 Loader 처리율을 확정하는 수치는 아니다. [측정 CSV](T-03_LOAD_results.csv)에는 등식 검사 횟수·stall 유지 cycle도 포함했다.

### 완료 펄스 보관의 관측

[즉시 성공 trace](T-03_case5_events.csv)에서 cycle 4,198은 **LD_RD2, mem_busy=0, loader_done=1**이다. 다음 cycle 4,199는 LD_WAIT이며 loader_done은 이미 0이다. 저장한 done을 읽어 cycle 4,200에 FINISH를 거쳐 완료했다. [즉시 실패 trace](T-03_case9_events.csv)도 같은 시점에 error를 함께 보관하여 결과 3을 기록한다. 늦게 발생하는 done뿐 아니라 상태 전환 전에 발생하는 완료 펄스도 확인했다.

### 오류 drain 근거와 한계

구간1 중간 오류는 Loader에 21 word를 전달한 뒤 나머지 **721 beat**를 버렸고, M00는 742 beat를 모두 받은 후 idle이 됐다. 구간2 오류는 누적 763 word를 전달한 뒤 **2,959 beat**를 버려 누적 3,722 beat로 read를 끝냈다. Top은 M00 busy가 내려가기 전에 종료하지 않았다. 구간1 마지막 beat 오류에서는 742 word가 이미 전달됐지만 오류가 우선하여 두 번째 read를 발행하지 않았다.

T-02d의 “M00가 오류 후 나머지 전송을 끝낸다”는 관측은 **소비 측 READY가 유지된 조건**이다. 별도 재현에서 RRESP 오류 후 READY=0으로 바꾸자 16 cycle 동안 busy=1이고 수락 수는 5/16에 머물렀다. READY=1 복구 후 16/16 완료했다. 이는 M00의 결함이 아니라 정상 handshake 의존성이다. Top의 임시 drain은 이 조건을 제공한다. [재현 명령·출력](T-03_ready_dependency_proof.txt)

메모리 오류 case에서 Loader stub은 예상량을 못 받아 active 상태로 남는다. 이번 단계는 **오류 결과와 M00 종료까지** 확인하며, abort 없는 Loader를 reset 없이 다시 시작할 수 있다고 주장하지 않는다. Loader 중단/재시작, cfg_ok 무효화, RD_FAULT 복구는 D08에서 정해야 한다. RD_FAULT는 READY=1로도 busy가 내려가지 않으므로 이 임시 drain만으로 복구되지 않는다.

두 상태/CSR 회귀 TB에는 짧은 **handshake 모형**만 넣었다. 실물 데이터 검사는 tb_top_load가 맡는다. 이 모형의 LOAD busy는 `DECODE 1 + LD_RD1 4 + LD_RD2 4 + LD_WAIT 2 + FINISH 1 = 12 cycle`이다. CSR 시험의 LOAD 2회와 다른 명령 5회로 총 `2×12 + 5×2 = 34 cycle`이다. 최초 기대값 32는 모형의 LD_WAIT cycle을 잘못 계산한 값이어서 34로 정정한 뒤 CSR와 나머지 회귀를 재실행했다. 이를 위해 RTL을 변경하지 않았다. 기존 2-cycle LOAD 가정과 미사용 출력 검사에서 새로 구현한 LOAD 출력을 분리했고, 상태를 강제로 늘리지 않았다.

Loader stub 자체의 검사도 임시 TB로 확인했다. non-idle START, 수락 전 data 변경, 예상량 이후 추가 beat를 각각 주어 **3/3 예상 fatal 검출**을 확인했다. 이 로그의 Fatal은 의도한 음성 시험이며 통합 시험의 실패와 구별한다. [검사기 음성 시험 전문](T-03_stub_checker_run.txt)

모형 자체시험 로그에도 검출기 검증을 위한 예상 위반 13건이 있다. **실물 M00 통합에서 위반 0**이라는 결과와 혼동하지 않는다. 최종 긍정 시험은 exit code뿐 아니라 성공 표식과 FAIL/Fatal 부재를 확인했다. xvlog, xvlog -sv, xelab의 최종 오류·경고는 모두 0이다.

## 5. 합성 점검

`pose_cnn_ctrl` 단독, `xc7z020clg400-1`, 기존 syn_check.tcl/잠정 100 MHz 제약, OOC 합성 결과다.

| LUT | FF | BRAM | DSP | Setup WNS | 래치 | 조합 루프 |
| ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| 146 | 77 | 0 | 0 | +1.986 ns | 0 | 0 |

Setup failing endpoint 0, TNS 0이다. 임계 경로는 `weight_addr_reg_reg[6]`에서 `mem_rd_addr[30]`으로 가는 주소 덧셈/출력 선택 경로다. 배치·배선 및 hold 검증은 하지 않았다. [syn/README 기록](../syn/README.md)

합성기는 도달 가능한 6상태를 3-bit sequential FSM으로 최적화했다. RTL의 13상태 4-bit 인코딩은 그대로이며 도면 대조/상태 복구 시험은 RTL 기준이다. 실제 FF 인코딩을 고정하는 속성을 추가하지 않았다.

첫 실행은 임시 작업 디렉터리의 `.Xil/.../realtime/tmp` 삭제 오류로 중단됐다. **RTL 변경 없이 프로젝트 syn 디렉터리에서 재실행해 합성 1회를 완료**했다. [최초 환경 오류 전문](T-03_synthesis_initial_issue.txt)

완료한 실행에는 기존 환경/제약/조회 관련 메시지가 있다: `Common 17-741` CRITICAL WARNING(Tcl store 권한), `Timing 38-242` WARNING(OOC HD.CLK_SRC 미지정), `Vivado 12-180` WARNING(래치 검색 결과 없음). 시뮬레이션 compile/elaboration의 경고 0과 합성 실행 전체의 메시지를 구별한다.
