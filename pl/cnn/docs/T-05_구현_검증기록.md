# T-05 — FC1 FIFO 스트리밍과 load_base_reg

2026-09-25. **FC1 RTL 및 독립 검증 구현 완료. 단계 전체 완료는 아님: P7 복구 방식과 P9 기존 INFER TB 수정 범위의 사용자 답변 대기.** 신규 통합 시험 11조건·14 INFER 실행, 기존 회귀 12 TB는 통과했다. 별도로 실행한 무수정 tb_top_infer는 기존 T-04 기대와 충돌하여 실패했다. T-06은 구현하지 않았고 Notion·팀 메시지는 전송하지 않았다.

## 1. 구현 전에 알린 명세 충돌

1. **P9의 무수정 tb_top_infer 통과는 현재 T-05 동작과 양립하지 않는다.** 기존 TB는 fc_done=0을 고정하고, FC 출력이 항상 0이며 ENC에서 FINISH로 가는 것을 검사한다. 이번 요구는 ENC에서 FC1을 시작하고 완료를 기다리는 것이다. 기존 입력 13조건을 유지하면서 FC1 완료 fixture만 연결하는 최소 수정 허용을 요청했다. 답변 전에는 해당 파일을 보존했다. 실제 실행도 첫 case에서 `LOAD/FC/write outputs remain zero` 검사로 실패했다.
2. **P7의 오류 후 재START 복구와 FC 중단 금지는 충돌한다.** 오류 이후 공급을 버리면 FC는 예상 word 수를 채우지 못해 active에 남고, 다음 START는 idle-only 계약에 어긋난다. `공통 reset → 재LOAD → 재INFER`를 복구 시험으로 인정할지 요청했다. 답변 전에는 오류 종료·drain까지만 검증했고, 재START 완전 복구를 PASS로 처리하지 않았다. FC를 몰래 중단하거나 stub이 자동 복구되도록 만들지 않았다.
3. 모든 word를 소비한 정상 done을 단순히 지연하는 것만으로 read 완료보다 앞당길 수는 없다. P5의 동시/조기 done은 **명시적인 제어 시험용 주입**으로 만들고 정상 완료 모드와 구분했다.
4. burst 정렬 기준은 LOAD base가 아니라 **FC1 read 주소(base+5,936)**다. LOAD base가 128 B 정렬이면 FC1 주소는 +48 B 비정렬이므로 현재 M00에서 3,073 burst다. base의 하위 7-bit가 0x50이면 FC1 주소가 정렬되어 3,072 burst다. 양쪽을 실제 시험했다.

충돌하지 않는 구현·시험·합성·전달 초안은 완료했다. 아래 신규 TB의 `ALL SELECTED`는 그 TB에 구현한 11조건을 의미하며 P7/P9까지 모두 완료했다는 표식이 아니다.

기존 소스 수정 3개, 신규 소스 2개다. 사전 기록 34파일 중 승인한 3개만 변경했고 **31파일 SHA-256 동일**이다. M00/S00/메모리 모형/기존 stub/Encoder와 보호 TB는 그대로다. Top의 포트 **45개 이름·방향·폭 동일**이며 내부 구동 방식만 일부 wire→reg로 바뀌었다. [정적 검사·해시](T-05_정적검사.json), [변경 diff](T-05_changes.diff).

```text
LOAD : IDLE → DECODE(load_base 저장) → LD_RD1 → LD_RD2 → LD_WAIT → FINISH
INFER: IDLE → DECODE → IN_RD → ENC → FC1 → FINISH → IDLE
                                    └ 오류: push 중지·READY=1 drain → FINISH(error=4)
```

| 도면의 상태/전이 | 이번 구현 |
| --- | --- |
| DECODE→LD_RD1 | 첫 LOAD read와 같은 edge에 weight_addr_reg를 load_base_reg에 저장. reset=0 |
| ENC→FC1 | enc_done일 때 fc_start=1, fc_sel=0, mem_rd_start=1을 같은 edge에 발행. 주소는 saved base+5,936, 길이 393,216 B. fc_done_seen=0 |
| FC1 정상 등식 | busy=1, fifo_we=mem_rd_valid&&!fifo_full, mem_rd_ready=!fifo_full, fifo_wdata=mem_rd_data |
| FC1 판정 | **read error 먼저**, 그 뒤 `(fc_done || fc_done_seen_reg) && !mem_rd_busy`. 완료 펄스가 먼저 와도 보관 |
| FC1 오류 | run_error=4, fifo_we=0, mem_rd_ready=1. M00 busy=0까지 현재 상태에서 drain. T-07 ERR_DRAIN 교체 주석 |
| 정상 FC1 탈출 | 이번에는 FINISH. T-06에서 FC2 및 fc_start(sel=1)를 붙일 자리만 주석으로 표시 |
| FINISH | 기존 D02 실행 결과·표시 분리, 기록 우선·sticky 유지 |

load_base_reg를 read 주소로 소비하는 곳은 ENC→FC1 한 곳뿐이다. LOAD 두 read는 기존 weight_addr_reg를 그대로 쓴다. `D06 required` 주석을 확정된 동작 설명으로 바꿨다. cfg_ok는 Loader의 모델 유효성을 나타내는 기존 계약을 따른다.

도면 XML과 다음 13개 localparam을 직접 대조했고 모두 일치했다. 직접 설계 RTL에 for/task/function/initial 등을 추가하지 않았고 동기식 active-low reset을 유지했다.

```text
IDLE=0000 DECODE=0001 LD_RD1=0010 LD_RD2=0011 LD_WAIT=0100
IN_RD=0101 ENC=0110 FC1=0111 FC2=1000 FC3=1001
WR=1010 ERR_DRAIN=1011 FINISH=1100
```

미구현 FC2/FC3/WR/ERR_DRAIN 4상태와 불법 값 13/14/15의 IDLE 복구 7조건을 상태 TB에서 통과했다. 합성기의 물리 FSM 인코딩은 아래 합성 절과 구분한다.

FC selector 변경은 DUT 출력에 force하지 않고 stub 입력만 START 이후 0→3으로 바꾼 것이다. 이 시험은 stub이 START에서 selector를 저장한다는 가정을 확인한다. 실물 FC의 latch 동작을 검증한 것은 아니다.

모든 신규 통합 명령 종료에서 `memory.check_quiescent`를 호출했다. 모형 AXI/C12 위반 0, consumer 검사 위반 0, FIFO overflow 0이며 `expect_violation`을 쓰지 않았다. 오류 실행 후 **AXI quiescent와 FC idle은 다르다**. FC active가 남은 것을 정상 완료로 간주하지 않는다.

### T-02b와 비교

T-02b의 ready=1, DDR 지연 0, 정렬 3,072 burst 기준은 **55,296 cycle = 1.125 cycle/beat**다. T-05 빠른 소비의 read busy가 정확히 같다. FIFO가 충분히 빨리 비워지면 추가 read 지연은 없다. FC1 체류 55,303에는 마지막 소비와 stub 완료 지연·상태 판정이 포함된다.

느린 소비 read는 194,561 cycle로 **139,265 cycle 증가**했고 valid/full stall 관측값과 일치한다. full cycle 145,322에는 RVALID가 없는 주소/전환 cycle도 포함되므로 이 값을 곧바로 추가 전송 지연으로 쓰면 안 된다. AR/R 정체를 겹치면 full R stall은 71,688로 줄지만 read busy는 같은 194,561이다. 공급 공백과 소비 병목이 겹치므로 두 지연을 단순 합산할 수 없다.

이번 회귀에서 T-02b 지연 0/16/32/64도 다시 실행했고 55,296/104,448/153,600/251,904 cycle을 유지했다. 실제 DDR 지연·AR outstanding 변경 여부를 이번 결과로 확정하지 않는다.

### FIFO stub 자체 검사

표준 FIFO처럼 empty일 때 그 edge의 push를 즉시 pop하지 않는다. 동시에 push/pop하면 count는 유지되고 기존 head가 먼저 소비된다. full인 edge는 pop 여부와 관계없이 외부 push를 금지한다. 전달 순서는 pushed/consumed 두 배열로 전량 검사했다.

별도 임시 단위 TB에서 full push, non-idle START, 잘못된 selector, X data, 예상 초과 push **5/5를 의도한 fatal로 검출**했다. 이 음성 시험의 Fatal은 실제 통합의 위반 0과 구분한다. [단위 소스](T-05_stub_checker_source.txt) · [명령·출력](T-05_stub_checks_run.txt). 초기 단위 시험의 초과 push 조건은 time 0 knob 설정이 stub 초기값과 경합하여 재현되지 않았다. 단위 TB의 설정을 reset 후 negedge로 옮겨 재실행했으며 RTL/stub의 계약은 바꾸지 않았다. [초기 기록](T-05_stub_checks_initial_issue.txt).

## 4. 회귀와 기존 INFER TB 충돌

상태/CSR의 짧은 모형은 기능 단계의 완료 handshake만 제공한다. 데이터 무결성과 실제 AXI는 신규 통합 TB에서 검사한다. 기존 D02/D03/CLEAR/snapshot/cfg_ok 관찰 시점 검사를 유지했고 FC1만큼 실행 길이를 늘렸다.

| --- | --- | --- |

통과한 회귀는 **12 TB, 21 xsim 호출**이다(상태/CSR/S00/M00/모형 11회 + LOAD 10회). 무수정 tb_top_infer의 실패 1회는 별도다. tb_ctrl_status는 최초 회귀에서 통과한 뒤 수정하지 않았다. ## 5. 합성 및 타이밍

기존 syn_check.tcl, `xc7z020clg400-1`, 잠정 100 MHz OOC 조건으로 **1회 합성**했다. 이후 RTL 변경 없이 TB와 문서만 정리했다.

| 단계 | LUT | FF | BRAM | DSP | WNS | 래치 | 조합 루프 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| T-04 | 239 | 120 | 0 | 0 | +1.734 ns | 0 | 0 |
| T-05 | 362 | 158 | 0 | 0 | **+1.408 ns** | 0 | 0 |
| 변화 | +123 | +38 | 0 | 0 | **−0.326 ns** | 0 | 0 |

Setup failing endpoint=0, TNS=0. **여유가 0.326 ns 감소**했으나 사용자가 정한 중단 경계 1.0 ns 아래로 내려가지 않았다. 임계 경로는 `weight_addr_reg_reg[6]/C → mem_rd_addr[28]`이며 9 logic level(CARRY4 7개 + LUT 2개)의 주소 가산/선택 경로다. 다음 경로는 `load_base_reg_reg[6]/C → mem_rd_addr[30]`, WNS +1.424 ns다. 임의의 타이밍 완화나 인터페이스 변경은 하지 않았다.

합성기는 도달 가능한 9상태를 4-bit sequential로 인코딩했다. RTL 도면의 13개 localparam이 물리 구현에 그대로 강제된다는 뜻은 아니다. P&R/hold는 이번 검증 범위가 아니며 WNS는 OOC 합성 추정치다.

합성 단계 자체 오류·경고는 0이다. 전체 실행에는 기존 `Common 17-741`(Tcl store 접근) CRITICAL WARNING, `Timing 38-242`(OOC clock 위치), `Vivado 12-180`(빈 래치 조회) WARNING이 있다. 시뮬레이션 compile/elaboration 경고 0과 구분한다. [합성 기록표](../syn/README.md) · [명령·출력 전문](T-05_synthesis_run.txt).

## 7. 검수 인계와 남은 범위

- **P7:** drain과 error=4는 확인했으나 FC는 active에 남는다. 오류 뒤 공통 reset·재LOAD를 복구 시험으로 인정할지 답변이 필요하다. reset 없는 재START 보장은 D08에서 결정한다.
- **P9:** tb_top_infer의 FC 미구현 가정을 보정할 최소 수정 허용 여부가 필요하다. 현재 파일은 보호했고 전체 회귀 통과로 쓰지 않았다.
- D06은 이번 코드에서 소비했다. D08의 FC 중단/복구·ERR_DRAIN, D09, 실물 FC·Encoder 결합은 확정하거나 구현하지 않았다.
- [지원에게 전달할 FC 요구사항 초안](T-05_FC_요구사항_초안.md)을 작성했다. 발송·Notion 등록은 하지 않았다.

다음 단계 예고: **T-06 — FC2 / FC3와 pose 출력 write(WR)**. 이번 작업에서 시작하지 않았다.
