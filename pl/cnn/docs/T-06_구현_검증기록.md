# T-06 — FC2/FC3/WR 정상 경로와 주소 경로 완화

날짜: 2026-09-25~26(시험 25일, 보고 정리 26일). 대상: Vivado 2020.2, `xc7z020clg400-1`.

**정상 INFER RTL 구현 및 Q1~Q6 시험은 완료했다. Q7의 보호 대상 `tb_top_fc1`은 현행 T-06 구조와 충돌하므로 단계 전체 완료로 표시하지 않는다.** 해당 TB 최소 보정 허용 여부를 사용자에게 질문했으며, 답변 전에는 수정하지 않았다. Claude 검수·사용자 확인 대기. T-07은 시작하지 않았다.

- 전 구간 TB: 기본 실행 10조건, 완료된 INFER 15회 PASS. 별도로 의도한 FC1 오류 뒤 비정상 재START 1회를 관측했다.
- 입력 TB: 기존 13조건/15회 PASS. T-04 대비 전체 실행 시간을 제외한 관측 필드 21개가 모두 동일하다.
- 상태/CSR 연결 2개, S00 4개, M00 4개, 메모리 모형 자체시험, LOAD 10조건 PASS.
- **주소 계산 등록만 적용한 T-05 구조**에서는 기존 `tb_top_fc1` 11조건/14회가 수정 없이 통과했고, T-05 LOAD/FC1 관측 줄 전체가 동일했다. 이것을 최종 T-06의 FC1 TB 회귀 통과로 대신하지 않는다.
- 합성 WNS: 동일 T-06 기능의 완화 전 **+1.406 ns**, 완화 후 **+1.728 ns**. 개선 **0.322 ns**. 래치/조합 루프 0.

## 1. 구현 전에 구분한 명세 문제

1. **동일 에지의 새 LOAD base 사용.** `load_base_reg <= weight_addr_reg`와 동시에 `fc1_addr_reg <= load_base_reg + 5936`를 쓰면 이전 LOAD base로 계산된다. 조합 next 값 `load_base_next = weight_addr_reg`를 정한 뒤 `fc1_addr_next = load_base_next + 5936`으로 계산했다. 최종 두 주소는 같은 LOAD 진입 에지에 저장된다.
2. **`mem_wr_ready`의 연속 HIGH는 여러 번의 정상 수락이다.** T-02c에서 확인한 M00는 W 채널 수락마다 READY를 내므로 연속 3 cycle HIGH가 가능하다. 0을 끼운 펄스 세 개를 강제하지 않고, 매 상승 에지의 HIGH 표본 수와 W 수락 수가 모두 3인지 검사했다. 빠른 case의 최대 연속 HIGH는 3, W stall case는 1이다. M00 수정은 없다.
3. **보호된 `tb_top_fc1`의 고정 기대와 T-06 기능이 충돌한다.** 이 TB는 FC1→FINISH, FC START 총 1회, write 출력 항상 0을 검사한다. T-06은 FC1→FC2→FC3→WR이므로 같은 조건을 만족할 수 없다. 추가로 확장된 stub의 `pose_data` 포트 연결이 빠져 xelab 경고가 발생한다. 최소 보정 허용 질문을 남기고 파일을 보존했다.
4. **입력 TB의 cfg_ok=1만으로는 주소 cache를 준비할 수 없다.** cache reset 값이 0이므로 TB 준비 단계에서 실제 LOAD를 실행해 base=0, FC1 주소=5936을 적재한다. 입력 13조건을 시작하기 전에 수행하고 입력 관측에는 포함하지 않는다. 난수 stall seed도 입력 시험 직전에 원래 값으로 복구했다.
5. FC2/FC3 stub 지연 0은 START 수락 다음 상승 에지의 완료, 즉 동기식 최소 지연 1 cycle로 정의했다. START와 같은 에지에 조합 완료를 만들어 이전 단계의 완료와 혼동시키지 않는다. 실제 FC 계약은 1-cycle done pulse이며, 레벨 done은 추가 내성 시험이다.

## 3. ASM-INFER와 구현 대조

기준은 `doc/pose_cnn_ctrl_fsm.drawio`의 ASM-INFER, 08_FC r10~16/r43~45/r109, 03_M00_AXI r17~23이다.

| 상태/전이 | 구현 및 확인 |
|---|---|
| ENC→FC1 | 완료 시 `fc_start=1, fc_sel=0`과 393,216 B read 동시 발행. 주소는 저장한 `fc1_addr_reg` |
| FC1 | 기존 FIFO 등식 유지. read 오류 우선, 다음으로 `(fc_done || fc_done_seen_reg) && !mem_rd_busy`. 정상 탈출에서 START/sel=1을 내고 FC2 |
| FC2(1000) | busy 유지. live/보관 done이면 START/sel=2를 내고 FC3. read/input/FIFO 동작 없음 |
| FC3(1001) | live/보관 done이면 write START, output snapshot, 24 B, beat=0을 내고 WR |
| WR(1010) | pose를 하위/중간/상위 64 bit 순서로 선택. READY 수락 우선으로 beat 증가. 그 외에는 실제 write busy 하강을 기다린 다음 error를 검사해 FINISH |
| WR 오류 | 마지막 B 수락 후 busy가 내려간 경우에만 error=5 기록. ERR_DRAIN 진입 없음 |
| 완료 보관 | FC1/FC2/FC3에서 done 보관, 각 FC START 에지에 보관값 0. 단계 간 이전 완료를 재사용하지 않음 |
| FINISH | 기존 D02대로 떠나는 에지에 done/error 표시 기록. CLEAR는 내부 실행 결과를 지우지 않음 |

WR의 beat는 0→1→2→3으로 진행한다. 3은 세 word를 모두 수락한 후의 값이며 증가를 멈춘다. B 응답을 기다리는 동안 상위 64 bit를 계속 내보내므로 범위를 벗어난 part-select나 X가 없다. `mem_wr_addr` 및 `mem_rd_addr` 자체를 FF에 저장하지 않았고 START 수락 에지의 주소 계약을 유지했다.

동작 예: FC3가 완료되면 output snapshot으로 24 B write를 시작한다. WREADY가 3 cycle 연속 허용되면 pose의 세 조각을 연속으로 전달하고 beat=3이 된다. B 지연 중에는 busy를 유지한다. B가 SLVERR이면 write 완료 후 FINISH에서 error=5를 표시한다.

ERR_DRAIN(1011)만 미구현이며 기존대로 IDLE 복구다. 13~15 불법 상태도 결과를 새로 만들지 않고 복구한다. read 오류의 기존 제자리 drain은 T-07/D08까지 유지했다.

## 4. Q1~Q7 관측

| 항목 | 결과와 관측값 |
|---|---|
| Q1 FC 연쇄 | 정상 0→1→2, START 각 1 cycle, START 시 FC idle. 단계마다 done 1회. START 밖 live selector를 뒤집어도 latched selector로 진행. 최소/지연/레벨 및 반복 실행 PASS |
| Q2 pose write 시작 | output snapshot 변경 내성, START 1회/1 cycle, 24 B. page-end `0x1e01ffe0`에서도 AW 1개, LEN=2, W 3개, 4 KiB 초과 없음 |
| Q3 데이터 | 매 WR cycle의 조각/beat 0~3 검사. READY 표본=실제 W 수락=3. 24개 byte 전량 일치, 바로 앞/뒤 64-bit guard 미기록 유지. W stall 중 순서 유지 |
| Q4 write 오류 | BRESP SLVERR 1회. W 3/B 1 완료, 마지막 W부터 B 수락까지 13 cycle(b_delay=12). busy 하강 후 error=5, ERR_DRAIN 미진입 |
| Q5 전 구간 | LOAD 3,722 word, 입력 1,440 word, FC1 push/pop 49,152 word 전량 대조. 정상 반복 2회 및 pose 유지 PASS. 실측 Encoder 지연 case 포함 |
| Q6 복구 | 입력 오류/FC1 오류/write 오류/정상 4종의 재START 결과를 다음 표에 분리 |
| Q7 회귀 | 상태·CSR·입력13·S004·M004·모형·LOAD10 PASS. **보호된 FC1 TB의 최종 RTL 회귀는 충돌로 실패. 최소 보정 답변 대기** |

통합 시험의 예상하지 않은 AXI/C12/RAM/FC 위반은 0이다. FC1 오류 뒤 재START의 계약 위반 1회는 Q6을 위한 의도한 관측으로 따로 기록했다. 정상 시험에 그 위반을 허용하지 않았다. 모형 `expect_violation`은 사용하지 않았다. 완료한 LOAD/INFER마다 `check_quiescent`를 호출했다.

확장 stub 검사기도 별도 음성 시험으로 확인했다. 예산 없는 non-idle START, selector=3, 선행 FC1 미완료 상태의 FC2 START 각각 정확한 이유로 fatal을 냈다. 3/3 탐지이며, 성공 회귀 로그와 분리한 [검사기 실행 전문](T-06_stub_checks_run.txt)이다.

## 5. D08 입력 — 오류 위치별 복구 가능성

| 위치 | 최초 실행 결과 | 공통 reset 없이 재START | 확인한 복구 |
|---|---|---|---|
| (a) 입력 read 중 | raw R 1,440, RAM 21 word 후 쓰기 중지, error=4. enc_start/FC START/write 모두 0 | **성공**. FC 시작 전이라 연산기가 idle | 입력 1,440/FC1 49,152/pose 24 B 전량 정상 |
| (b) FC1 read 중 | FC1 공급 1,285 word, FIFO 이후 47,867 beat는 DDR drain. error=4, FC active 유지 | **계약 위반으로 거부**. 다음 FC1 START에서 old FC active=1, consumed=1,285/49,152 관측 | **공통 reset → LOAD → INFER 성공**. FC·FIFO·두 주소 cache 초기화 후 전량 정상 |
| (c) pose write 중 | FC3 종료 후 B 오류, 24 B 전송 완료, error=5 | **성공**. 이전 FC는 이미 idle | 다음 INFER의 pose 24 B 정상 |
| (d) 오류 없음 | done=1/error=0 | **성공**. 연속 2회 정상 | 이전 pose는 다음 FC3 완료까지 유지 |

(b)에서 stub은 FC를 자동 중단하거나 새 START로 초기화하지 않는다. Q6 전용 `expected_busy_starts=1`을 TB가 명시해 **거부 사실과 기존 active 상태를 보존한 채** 관측한다. 위반을 확인한 뒤 시험을 중단하고 공통 reset을 가했다. 실제 FC의 미정 동작을 추측해 영구 정지라고 단정하지 않으며, **현재 idle-only 계약으로 재START 복구를 보장할 수 없다는 근거**다. D08 정책 자체는 결정하지 않았다.

## 6. 전 구간 cycle 측정

START 수락 에지부터 Top busy 하강까지. LOAD는 INFER 시간에서 제외한다. FC의 실제 수학 연산은 없고, DDR 최초 응답 지연은 0이다. FC 기본 지연은 FC1 완료 후 5, FC2=3, FC3=4 cycle이다.

|---:|---|---:|---|---:|---|
| 0 | 정상, 연속 2회 | 56,947 / 56,947 | 55,303 / 4 / 5 | 0 | 각 24 B |
| 1 | FC 최소 지연 | 56,937 | 55,298 / 2 / 2 | 0 | 24 B |
| 2 | FC 지연 25/50/100 | 57,110 | 55,323 / 51 / 101 | 0 | 24 B |
| 3 | FC 완료 레벨, 연속 2회 | 56,947 / 56,947 | 55,303 / 4 / 5 | 0 | 각 24 B |
| 4 | AW/W stall, B 지연 20, page-end | 56,977 | 55,303 / 4 / 5 | 0 | 24 B, 마지막 W→B 21 cycle |
| 5 | 입력 read 오류 → 재START | 1,623 / 56,947 | 오류 실행 0 / 0 / 0 | 0 | 오류 실행 write 0, 다음 24 B |
| 6 | FC1 오류 → reset/LOAD → INFER | 58,572 / 56,947 | 오류 실행 56,943 / 0 / 0 | 오류 실행 1,718 | 오류 실행 write 0, 복구 후 24 B |
| 7 | write 오류 → 재START, B 지연 12 | 56,959 / 56,959 | 55,303 / 4 / 5 | 0 | 모두 24 B, 결과만 5→0 |
| 8 | Encoder 지연 **1,278,890** | **1,335,832** | 55,303 / 4 / 5 | 0 | 24 B |
| 9 | 느린 FC와 read stall | 200,237 | 196,614 / 4 / 5 | 119,484 | 24 B |

정상 입력 AR=90, FC1 AR=3,072. LOAD base는 `0x1c000050`, INFER 시 live WEIGHT_ADDR는 다른 `0x1c100050`, 발행 FC1 주소는 저장된 base의 `0x1c001780`이다. LOAD 두 구간은 47+187 AR, 4,195 cycle이며 case 9의 stall 조건에서는 9,313 cycle이다.

## 7. tb_top_infer 보정과 회귀의 경계

|---|---|
| 216~231 | 192-bit pose와 기존 Loader stub 연결. LOAD 준비 중만 Loader ready 사용. 실제 IN_RD에서는 계속 ld_ready=0으로 두어 입력 READY=1 독립성을 검증 |

| 372~374 | 입력 beat 관측은 FC1 시작 전까지 유지. 이후 WR이 같은 beat 레지스터를 0으로 재설정하는 것을 입력 카운터 오류로 판단하지 않음 |

| 461~471/502 | 각 case 전 LOAD를 완료해 주소 cache 준비. 기존 입력 결과/관측 카운터의 시작점에는 포함하지 않음 |
| 503~504 | LOAD가 사용한 PRNG 진행을 원래 입력용 seed `0x23456789`로 되돌림. random stall 입력 시간도 T-04의 3,057 cycle로 동일 |

13조건/15회에서 T-04 CSV의 `total_cycles`만 FC2/FC3/WR 추가로 달라졌다. 다른 **21필드×15회가 전부 동일**하다. 입력 주소 0~1439 유일성, 90/91 AR, NO_CFG, 중간/마지막 RRESP, 오류 시 Encoder 미발행, error_then_restart를 유지했다. 첫 실행에서 난수 case의 입력 시간이 3,069였던 이유는 준비 LOAD가 seed를 진행시킨 것이었으며, seed 복원 후 입력 TB 전체를 재실행했다. [최종 입력 CSV](T-06_INFER_results.csv)

상태 TB는 D02/D03·snapshot·busy 중 START 무시를 그대로 검사하고, 미구현/불법 복구는 ERR_DRAIN 및 13~15의 4개로 좁혔다. CSR 연결 TB의 모형 INFER는 35 cycle이며 총 busy 표본은 100, START 7, busy read 49, busy 중 command 거부 1회다. S00/M00/LOAD 원본의 기대값은 바꾸지 않았다.

### 보호된 FC1 TB의 미해결 회귀

현재 원본 `tb_top_fc1.v:224`는 새 pose 출력이 미연결이라 xelab에서 `VRFC 10-3645` 1건을 낸다. 진단 목적으로 만들어진 snapshot을 실행하면 첫 정상 case의 FC1→FC2 전이에서 323행의 `FC1 starts after complete input/Encoder` 검사가 실패한다. 이 검사는 모든 FC START에 read START가 동반되어야 한다는 이전 단계 가정이다. 이후에는 FINISH=12 고정 기대, START/완료 각 1회, write 출력 0 기대도 충돌한다.

따라서 최종 Q7 전부 PASS 또는 모든 대상의 xelab 경고 0으로 쓰지 않는다. 실패를 숨기기 위해 RTL을 T-05로 돌리거나 FC2/3을 자동 중단하지 않았다. [원본 TB 경고·실패 재현 전문](T-06_legacy_fc1_issue.txt)

보정 시에도 기존 FIFO 데이터/주소/속도 조건을 유지해야 한다. 특히 case 5/6은 실제 FC 완료 계약과 다른 **강제 조기 done 주입**이다. 소비가 끝나기 전에 done을 내므로 후속 FC2 START의 idle 계약과 충돌할 수 있다. 이 두 조건은 FC1 단독 제어 시험으로 분리하는 방식까지 포함해 보정 허용 여부를 질문했다. 현재는 주소 완화 단독 비교에서 원래 11조건/14회를 모두 실행하여 이전 관측값이 유지됨을 보였다.

## 8. 주소 완화 전후 합성

같은 T-06 기능을 기준으로 출력 mux의 두 주소만 원래 덧셈식으로 되돌린 비교본과 최종본을 각각 1회 합성했다. `mem_rd_addr`/`mem_wr_addr` 출력 FF화나 START 지연은 하지 않았다.

| 버전 | LUT | FF | BRAM/DSP | WNS | 래치/조합 루프 |
|---|---:|---:|---|---:|---|
| T-05 기준 | 362 | 158 | 0/0 | +1.408 ns | 0/0 |
| T-06 동일 기능, 완화 전 | 475 | 191 | 0/0 | +1.406 ns | 0/0 |
| **T-06 최종, 완화 후** | **471** | **220** | **0/0** | **+1.728 ns** | **0/0** |

- 완화 효과: WNS **+0.322 ns**, LUT −4, FF +29. 최적화 후 자원 수이므로 RTL의 64-bit cache 추가를 물리 FF +64라고 쓰지 않는다.
- T-05 대비 최종 WNS **+0.320 ns**. 1.0 ns 중단 기준을 넘지 않았다.
- 완화 전 임계: `weight_addr_reg_reg[6]/C → mem_rd_addr[30]`, CARRY4 7개를 포함한 9 logic level.
- 완화 후 임계: `cmd_reg_reg[15]/C → mem_rd_addr[0]`, 4 LUT level. 주소 출력까지의 가산기가 빠지고 명령 판정/주소 선택이 임계가 됐다.
- 두 실행 모두 setup failing endpoint 0, TNS 0. 기존 잠정 100 MHz OOC 조건이며 P&R/hold 검증은 하지 않았다.
- `synth_design` 자체 오류/경고 0. 전체 실행에는 기존 Tcl store `Common 17-741`, OOC clock `Timing 38-242`, 빈 latch 조회 `Vivado 12-180` 메시지가 각각 존재한다. 이를 시뮬레이션 compile/elaboration의 경고 0과 혼동하지 않는다.

주소 완화만 적용한 T-05 비교본에서 원본 FC1 11조건/14회, LOAD 10조건, 상태/CSR TB가 모두 통과했다. FC1·LOAD 출력 관측 줄은 이전 로그와 동일했다. 이후 최종 T-06에서는 허용된 TB만 상태 확장에 맞췄다. 따라서 FC1 원본 회귀 실패를 주소 완화에 의한 기능 변경으로 해석하지 않는다.
