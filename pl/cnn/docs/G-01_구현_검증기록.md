## 2. 구현 전에 보정한 명세 해석

1. `test_expected_pose`는 현재 weight와 현재 입력의 기대값이다. 새 blob에 그대로 적용하면 잘못된 실패가 된다.
   기존 샘플일 때만 기대값과 비교하고, 모든 지정 blob/input은 **원본 C++ 대 관측 C++의 최종 float32 비트**를 비교한다.
2. input scale 변경은 RTL 포트를 바꾸지 않지만 PS의 입력 양자화에 영향을 준다.
   `--input-bin`을 추가해 새 scale로 양자화한 입력을 받는다. 생략 시 기존 INT8 샘플을 그대로 사용한다는 안내를 낸다.
3. 고정 `WEIGHT_OFFSETS`는 **구조가 그대로일 때만** blob 배치가 유지되는 근거다.
   채널/레이어/텐서 형상이 바뀌어도 안전하다는 뜻이 아니다. exporter의 단순 offset 상수만으로 그 변경을 보호할 수 없다.
4. shift 경계는 단순 `frexp` 지수만이 아니라 multiplier 반올림으로 지수가 1 증가하는 경우까지 반영했다.

참고 C++는 blob header를 직접 검사하지 않는다. 실행기에 size/magic/version/count/scale 검사를 두고,
Python 진입부에서 Loader와 같은 shift 범위를 확인했다. 모델 연산식은 바꾸지 않았다.

## 5. r44 — weight 내부 순서 확정

**확정 범위: 현재 v6 C++/v2 exporter와 동일한 구조의 blob.**
출력 neuron 우선, 입력/tap이 안쪽인 순서다. Conv 공유 weight는 세 receiver bank에 같은 값으로 복제되며 blob에 rx 축은 없다.
주소 offset 검증을 반복한 것이 아니라 offset 내부 인덱스를 확인했다.

### Conv1 / Conv2

`full_pose.cpp` **165~167행**, **200~202행**의 실제 코드:

```cpp
const int index = (((oc * RECEIVER_CHANNELS + ch) * 5 + kh) * 3 + kw);
g_conv1_weight_int8[bank][oc][ch][kh][kw] =
    read_packed_i8(weights, WEIGHT_OFF_CONV1_WEIGHT, index);

const int index = (((oc * CONV1_OUT + ic) * 3 + kh) * 3 + kw);
g_conv2_weight_int8[bank][oc][ic][kh][kw] =
    read_packed_i8(weights, WEIGHT_OFF_CONV2_WEIGHT, index);
```

| 구간 | C++ byte index 전개 | RTL 상주 RAM 배치 | 판정 |
|---|---|---|---|
| Conv1, KH=5/KW=3/IC=3 | `n=oc*45+tap`, `tap=(ch*5+kh)*3+kw` | word=`tap`, lane=`oc` | 09 r25 일치 |
| Conv2, KH=3/KW=3/IC=16 | `n=oc*144+tap`, `tap=(ic*3+kh)*3+kw` | word=`45+(oc/16)*144+tap`, lane=`oc%16` | 09 r29 일치 |

따라서 축 순서는 `[oc][ic][kh][kw]`다. 사본의 C++ 인덱싱은 기존 blob→RAM scatter 주소식과 맞는다.

### FC1 / FC2 / FC3 및 FC1_PACK

`full_pose.cpp` **549~557행**:

```cpp
int base = o * (FLATTEN_DIM / FC1_PACK);
packed_weight_t packed = weights[WEIGHT_OFF_FC1_WEIGHT + base + i / FC1_PACK];
acc0 += mul_i8_dsp(read_banked_flatten(input, i + 0), unpack_i8(packed, 0));
acc1 += mul_i8_dsp(read_banked_flatten(input, i + 1), unpack_i8(packed, 1));
acc2 += mul_i8_dsp(read_banked_flatten(input, i + 2), unpack_i8(packed, 2));
acc3 += mul_i8_dsp(read_banked_flatten(input, i + 3), unpack_i8(packed, 3));
```

`FC1_PACK=4`는 **32-bit word 하나에 연속 입력 weight 4개**라는 뜻이다. 출력 채널 4개를 묶는 포맷이 아니다.
`unpack_i8`(97~103행)은 `word.range(byte_index*8+7, byte_index*8)`를 읽는다.
따라서 낮은 byte가 먼저다. FIFO 64-bit beat는 이 packed word 2개를 같은 순서로 붙인다.

| 레이어 | blob 구간 내부 byte | 32/64-bit 대응 |
|---|---|---|
| FC1 | `o*3072+i` | C++ word=`o*768+i/4`, byte=`i%4`; FIFO beat=`o*384+i/8`, lane=`i%8` |
| FC2 | `o*128+i` | FCW word=`o*16+i/8`, lane=`i%8` |
| FC3 | `o*128+i` | FCW word=`2048+o*16+i/8`, lane=`i%8` |

FC2 loader **248~249행**과 FC3 **260~261행**은 각각
`read_packed_i8(..., o * HIDDEN_DIM + i)`로 `weight[o][i]`를 채운다.
계산부 **312~316행**도 `input[i] * weight[o][i]`다. 세 FC 모두 `[출력][입력]` 순서가 확정된다.

exporter `generate_assets.py` **116~123행**도 C-order `reshape(-1)` 후
`u8[:,0] | (u8[:,1]<<8) | (u8[:,2]<<16) | (u8[:,3]<<24)`로 little-endian 포장한다.
FC 덤프에 대해 독립 Python dot product와 누산값 280개를 대조한 결과도 일치했다.

## 6. Flatten 순서 확정

`full_pose.cpp` **470행**은 `(c*POOL_H+oh)*POOL_W+ow`, 전역은 rx bank를 앞에 붙인다.

```text
byte n = ((rx*32+oc)*8+oh)*4+ow
word   = rx*128 + oc*4 + floor(oh/2)
lane   = (oh%2)*4 + ow
```

명세 07_Flatten r12, 실제 `Pool.v:135` byte 주소와 `:146` byte-enable write의 대응이 같다.
포함되는 값은 Conv2 GELU 이후 **adaptive pooling까지 끝난 결과**다.

## 7. 재학습 영향 경계

전제: 동일한 구조, INT8/INT32 폭, zero-point와 반올림·포화·LUT 인덱스 계약을 유지하고 모든 파라미터를 함께 재export한다.

| 바뀌는 항목 | RTL 영향 | 함께 해야 할 일/조건 |
|---|---|---|
| Conv/FC weight 값, bias, requant_mult | 배선·주소·RAM 크기 변경 없음 | 새 blob 전체 재생성·LOAD. 정수 폭 유지 |
| GELU LUT 내용 | RAM 내용만 변경 | 새 input/output activation scale로 LUT도 재생성 |
| input scale | RTL 포트 변경 없음 | **PS 입력 양자화 갱신**, 새 golden INT8 입력 공급 |
| output scale | RTL 포트 변경 없음 | header/CSR scale과 PS의 INT8→float 변환을 함께 갱신 |
| pool_mult / pool_shift | 값만 교체 가능 | shift 범위 확인, 새 모델로 수치 검증 |
| 레이어별 requant_shift | **주의** | 328개 전부 −31..63. 벗어나면 Loader가 거부하며 검사 완화로 통과시키지 않음 |
| Conv1 16 / Conv2 32 / hidden 128 / pose 24 | **재설계 필요** | 주소맵·상주 RAM·FC weight 크기·전송량·제어·golden 도구 형상 변경 |
| 입력 9×128×10, receiver 수, Pool 8×4 | **재설계 필요** | 입력 11,520 B, flatten 3,072 B와 모든 하위 인덱스·beat 수 재검토 |
| 레이어 순서/커널/stride/padding/양자화 방식 | **재설계 또는 연산 계약 재검토** | 값 교체만으로 지원하지 않음 |

`generate_assets.py:24~59`의 offset 상수는 구조 고정의 증거다. 이 exporter는 텐서 형상 변경을 전부 검출하는 도구가 아니므로,
구조가 바뀐 weight를 같은 offset에 억지로 넣으면 구간이 겹칠 수 있다. offset 불변을 구조 독립성과 혼동하면 안 된다.

`int8_export.py:207~210`:

```python
codes = torch.arange(-128, 128, dtype=torch.float32)
values = F.gelu(codes * safe_scale(input_scale))
return torch.round(values / safe_scale(output_scale)).clamp(INT8_QMIN, INT8_QMAX).to(torch.int8).numpy()
```

GELU 함수와 코드 순서 −128..127은 고정이지만, LUT 내용은 두 scale에 의존한다.
signed q의 `q+128`은 8-bit 비트 표현에서 **`q_bits XOR 0x80`**과 같다.
참고 C++ **570행**도 `lut[(int)input[i] + 128]`이다. `int8_export.py:331`에 인덱스 표기가 명시돼 있다.
현재 포화 범위는 −127..127이며 −128 index 역시 테이블에 존재한다.

캘리브레이션 근거: `SampledAbsObserver.update`(**77~90행**)는 데이터의 절댓값을 수집하고,
`scale`(**92~101행**)은 percentile/max 범위로 scale을 만든다.
`observers.observe`(**146~174행**)가 각 레이어/활성/Pool 출력을 관측하므로 데이터셋이 달라지면 scale과 LUT도 달라질 수 있다.

### shift 범위 이탈 조건

`int8_export.py:28~38`의 실제 `quantize_multiplier`를 읽고, 함수만 AST로 추출해 경계 6개를 실행했다.

```text
real_scale r = safe(input_scale) * safe(weight_scale[o]) / safe(output_scale)
pool r       = encoder.gelu2_scale / encoder.pool_scale
(m,e)        = frexp(r), 0.5 <= m < 1
mult         = round(m * 2^31)
mult == 2^31 이면 mult/=2, e+=1
shift        = 31-e
```

**최종 보정 후 지수 e가 −32..62여야 shift가 −31..63에 들어간다.**
대략적인 r 구간은 `2^-33 <= r < 2^62`지만, 정확히는 multiplier 반올림 때문에 경계가 조금 아래로 이동한다.
현재 Python `round` 규칙에서 **양수·유한 r**의 허용 구간은:

```text
L = (1 - 2^-32) * 2^-33 = 1.1641532179982976e-10
U = (1 - 2^-32) * 2^62  = 4.6116860173536461e18
허용: L <= r < U
r < L  → shift > 63
r >= U → shift < -31
```

| exporter 실측 | shift |
|---|---:|
| L 바로 아래 / L / 바로 위 | **64 / 63 / 63** |
| U 바로 아래 / U / 바로 위 | **−31 / −32 / −32** |

즉 입력·weight scale에 비해 출력 scale이 너무 크면 r이 작아져 shift 상한을 넘고,
반대로 출력 scale이 너무 작으면 r이 커져 하한을 넘는다. pool도 두 activation scale의 비율로 같은 검사를 적용한다.
원본 함수의 r<=0 예외는 `(0,0)`이지만 정상 exporter는 양수 scale을 사용한다. NaN/무한은 이 구간 식의 대상이 아니다.

| 현재 항목 | min..max shift | 상한 63까지 최소 여유 |
|---|---|---:|
| Conv1 | 39..40 | 23 |
| Conv2 | 39..40 | 23 |
| FC1 | 40..44 | **19** |
| FC2 | 39..41 | 22 |
| FC3 | 42..43 | 20 |
| Pool | 31 | 32 |

새 blob마다 범위를 검사해야 한다. 현재 여유로 미래 재학습을 보장하지 않는다.
또한 이 범위는 Loader 수락 조건이며 모든 데이터의 수치 안전성 증명은 아니다.
참고 C++의 native `long long` shift/rounding과 32-bit 누산 폭이 있으므로 극단적인 scale·bias에는 overflow/언어상 shift 제약도 있다.
원본 알고리즘을 바꾸지 않았고, 새로운 모델의 golden 생성 및 RTL 수치 대조를 별도로 수행해야 한다.
