# L-05 실제 reference blob Loader 검증

작성: 2026-09-26, Codex. L-05 구현·자체 검증 완료. RTL 수정·합성 없음. Claude 검수와 사용자 확인 전이며 다음 단계는 시작하지 않았다.

실제 **422,992-byte blob**으로 `weight_param_loader`를 실행했다. 3,722beat를 수락하고 **done=1 / err=0 / cfg_ok=1**, 9,772cycle에 완료했다. 외부 읽기 포트로 Conv/Param/LUT/FCW 전체를 대조한 결과 **불일치 0**이다. 기존18TB도 무수정 통과했다.

다섯 레이어의 shift328개는 모두 허용 범위 안이다. GELU 네 테이블은 서로 다르지만 각각5/7/12/32개의 감소 구간이 있다. 분포와 감소 위치를 아래에 관측값으로 남겼으며 RTL·데이터·검사를 고쳐 통과시키지 않았다. **r44의 텐서 축 순서와 추론 정확도를 최종 확정한 결과는 아니다.**

## 1. 입력 파일과 읽기 방식

구현 전에 두 후보를 발견해 사용자에게 알렸다. 두 파일의 크기와 SHA-256이 같아 동일 내용임을 확인하고 HLS 경로를 선택했다.

| 용도 | 정확한 경로 | 크기 |
|---|---|---:|
| 실제 시험 입력 | [HLS reference blob](D:/2609_final_project/wifi-csi-pose-main/HLS/pl_accel_v6/pl_accel_v6_weights.bin) | 422,992byte |
| 같은 내용의 배포본 | [PS 배포용 blob](D:/2609_final_project/wifi-csi-pose-main/petalinux/tools/pl_accel_v6/pl_accel_v6_weights.bin) | 422,992byte |

두 파일의 SHA-256:

```text
063d01b880c4d96f1fe61450a72a9911b222ebf67bbbbf560da700a7350b94bb
```

TB는 원본을 `$fopen(path,"rb")`와 `$fread`로 직접 읽는다. 8-bit 배열로 읽은 뒤 little-endian 32/64-bit 값을 명시적으로 조립하므로 `$fread`의 packed-word byte 순서에 의존하지 않는다. 읽은 길이가422,992이고 추가 `$fgetc`가 EOF인지 확인했다. **blob 복사·bin→hex 변환·중간 데이터 파일은 없다.** `+BLOB=<path>`로 경로를 바꿀 수 있으며 기본은 위 HLS 절대 경로다.

header와 offset 근거는 [full_pose.h](D:/2609_final_project/wifi-csi-pose-main/HLS/pl_accel_v6/full_pose.h:25) 및 원문 XLSX `09_Loader_주소맵` r7~r44다. 기존RTL을 기준으로 golden 주소식을 복제하지 않았다.

## 2. B1/B6 — 실제 header, word0~7 총8개

| word | 의미 | 실제 32-bit hex | 의미에 맞는 해석 |
|---:|---|---|---|
| 0 | magic | `0x36574C50` | 기대 magic과 일치 |
| 1 | version | `0x00000002` | 2 |
| 2 | total_words | `0x00019D14` | 105,748word; ×4=422,992byte |
| 3 | input_scale | `0x3CB76ADB` | float32 **0.022389819845557213** |
| 4 | output_scale | `0x3BD997A8` | float32 **0.006640393286943436** |
| 5 | pool_mult | `0x783B66B4` | signed32 **2,017,158,836** |
| 6 | pool_shift | `0x0000001F` | signed32 **31**, 범위[-31,63] 안 |
| 7 | 예약 | `0x00000000` | 0 |

word3/4는 Python의 little-endian float32 해석으로 **유한한 양수**임을 확인했다. NaN/Inf/음수/0이 아니며 숫자 표현상 scale로 사용할 수 있는 값이다. 해당 scale의 모델 보정 정확성은 이번 시험으로 판정하지 않는다. word7은 예약 정수이므로 float로 해석하지 않는다.

TB의 header8개 출력과 Python 분석 결과는 전부 일치한다. LOAD 완료 시 `output_scale_bits`, `pool_mult`, `pool_shift`도 각각 파일 word4/5/6과 비트 단위로 같았다. word3/7은 Loader가 쓰지 않는 값으로 유지했다.

## 3. B2/B3 — 실제 두 LOAD 구간

| 구간 | 원본 word 범위 | 원본 byte 범위(끝 제외) | 크기 | 전송 beat |
|---|---|---|---:|---|
| LOAD 구간1 | [0,1484) | [0,5936) | 5,936B | 0~741, 742개 |
| 건너뛴 FC1 weight | [1484,99788) | [5936,399152) | **393,216B** | LOAD에는 없음 |
| LOAD 구간2 | [99788,105748) | [399152,422992) | 23,840B | 742~3721, 2,980개 |

393,216B = (99,788−1,484)×4 = 128×3,072×1byte로 HLS의 FC1 출력/입력 크기와 일치한다. 전송 합계는29,776B / 8 = **3,722beat**다. 마지막 byte는 파일 끝과 정확히 맞는다.

TB는 beat0~741을 offset=`beat×8`, beat742~3721을 offset=`399152+(beat−742)×8`에서 만든다. beat741은 offset5928, beat742는399152, 마지막 beat3721은422984다. 하위32bit는 짝수 word, 상위32bit는 홀수 word다. 매 handshake에서 전송값을 원본 byte열과 대조하고 READY가 낮으면 같은 beat를 유지한다.

실제 실행:

```text
OBS: L-05 B3 RESULT beats=3722 cycles=9772 ready_low=6050 done_pulses=1 done=1 err=0 cfg=1
```

header/shift 검사에 실제 모델이 거부되는 경우는 없었다. 이후 읽기 동안 cfg_ok=1이 유지되고 done/err는0으로 돌아갔다. Top/M00 연결 시험이 아니라 **두 read 구간을 재현한 Loader 단독 시험**이다.

## 4. B4 — 파일로 만든 golden과 외부 포트 전량 대조

golden은 TB가 원본 파일에서 독립 계산한다. Conv golden은 `/`·`%`를 쓰고 RTL은 기존 tap/oc 카운터를 그대로 사용한다.

| RAM | golden 계산 | 외부 포트 대조 단위 | 불일치 |
|---|---|---:|---:|
| Conv | Conv1 byte n→word n%45/lane n/45. Conv2→word45+((n/144)/16)×144+n%144, lane(n/144)%16 | **5,328byte** | **0** |
| Param | 아래 layer별 원본 bias/mult/shift word를 RAM `{shift,mult,bias}`로 조립 | **328주소×3=984필드** | **0** |
| LUT | 원본 byte421968+i→주소i | **1,024byte** | **0** |
| FCW | FC2 byte400688+8a→주소a; FC3 byte418608+8a→주소2048+a | **2,432word(64bit)** | **0** |

| 레이어 | Param RAM base | 개수 | 원본 bias word | mult word | shift word |
|---|---:|---:|---:|---:|---:|
| Conv1 | 0 | 16 | 188 | 204 | 220 |
| Conv2 | 16 | 32 | 1388 | 1420 | 1452 |
| FC1 | 48 | 128 | 99788 | 99916 | 100044 |
| FC2 | 176 | 128 | 104268 | 104396 | 104524 |
| FC3 | 304 | 24 | 105420 | 105444 | 105468 |

golden의 Conv주소333×16 bitmap도 미기록0/중복0이다. 이는 **golden 주소식의 coverage 검사**이고 내부 DUT 쓰기 횟수를 관측한 것은 아니다. DUT 결과는 내부 계층 참조 없이 상위 읽기 포트로 확인했다.

2,432clock 동안 RAM4종을 병렬 읽고 각 유효 주소의 모든 byte/field/word를 비교했다. 현재 D09는 enc 고정이므로 Param/LUT 전체 주소를 enc 포트로 읽고 FC측 데이터 출력도 같은지 확인했다. FC 선택을 강제로 켜거나 내부 RAM을 읽지 않았다. FC1 weight는 LOAD 대상이 아니므로 FCW 대조에는 포함되지 않으며, 아래 분포 분석에는 포함된다.

```text
OBS: L-05 B4 READBACK conv_bytes=5328 param_fields=984 lut_bytes=1024 fcw_words=2432 mismatches=0/0/0/0 hierarchy_reads=0 clocks=2432
PASS: L-05 B4 RAM_PORT_READBACK all_compared=1 mismatches=0
```

## 5. B5 — 실제 값 분포

아래 수치는 Python 파일 분석과 TB의 독립 통계를 서로 대조해 일치함을 확인했다. weight/LUT는 signed INT8, shift는 signed32로 해석했다. **byte를 signed8로 해석하면 [-128,127] 안에 드는 것은 표현 자체의 성질**이므로, 그 범위에 든다는 사실만으로 tensor 축 순서가 옳다고 판단하지 않았다.

pool_shift31은 별도 header 항목이다. 실제 shift가 범위 밖인 index는 없었다. TB는 발견할 경우 layer/index/blob word/byte offset/value를 출력하고 실패하도록 작성했으며 제한을 완화하지 않았다.

### GELU LUT — 단조성의 수치화

각256entry를 주소0→255 순서로 읽고 인접255쌍의 증가·동일·감소를 센다. 명세의 `uint8(q) XOR 0x80` 주소와 [참고 exporter의 q=−128..127 순서](D:/2609_final_project/wifi-csi-pose-main/ML/src/int8_export.py:207)에 맞춰 q=index−128로 위치를 표시했다. 여기서는 감소 유무를 PASS/FAIL 조건으로 쓰지 않았다.

| table | 대상 | 최소 | 최대 | 0 개수 | 증가쌍 | 동일쌍 | 감소쌍 | 최대 감소폭 |
|---:|---|---:|---:|---:|---:|---:|---:|---:|
| 0 | Conv1 | −5 | 127 | 69 | 113 | 137 | **5** | 1 |
| 1 | Conv2 | −7 | 127 | 73 | 73 | 175 | **7** | 1 |
| 2 | FC1 | −12 | 127 | 86 | 36 | 207 | **12** | 1 |
| 3 | FC2 | **−48** | 127 | **1** | 77 | 146 | **32** | 1 |

감소하지 않는 쌍은 각각250/255, 248/255, 243/255, 223/255다. **네 테이블 모두 엄밀한 단조증가는 아니다.** 특히 FC2는 첫 값−16, 최소−48이고 감소32곳으로 다른 테이블과 분포 차이가 크다. 관측값을 기록하며 결함 또는 정상 모델 곡선이라고 최종 판정하지 않는다.

감소가 시작되는 index(즉 value[index+1] < value[index])는 다음과 같다. 위치를 재현하려면 `byte offset=421968+256×table+index`를 읽으면 된다.

|---:|---|
| 0 | 67,80,88,95,103 |
| 1 | 71,82,88,92,96,100,105 |
