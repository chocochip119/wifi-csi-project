# L-03 Conv Weight byte scatter 구현·검증

작성: 2026-09-26, Codex. L-03 구현·자체 검증 완료. Claude 검수와 사용자 확인 전이며 L-04/코어 통합은 시작하지 않았다.

Conv1/Conv2 scatter를 구현해 정상 LOAD에서 Conv RAM **5,328 byte 전부를 정확히 한 번씩** 기록했다. 미기록·중복·데이터 불일치는 모두 0이다. Param/FCW/LUT 검증과 총 **9,772 cycle / READY low 6,050**도 유지됐다.

최초 합성은 WNS **−0.016 ns**로 실패했다. Conv 주소 경로에서 불필요한 현재 입력의 header/shift 판정을 분리한 최종본은 같은 제약에서 **+1.365 ns**다. LUT631/FF212/RAMB36 10+RAMB18 3/DSP0, 래치·조합 루프0. 수정 전후 TB 성공 관측561줄이 동일했다.

## 1. 구현 전 원문 확인과 범위 해석

`Pose_CNN_IP_Interface_Spec.xlsx`의 `09_Loader_주소맵` r25/r29를 직접 읽고, 주소식을 별도 Python 계산으로 전개했다. 333×16의 모든 `(word,lane)` 조합이 정확히 한 번 나타났으며 원문의 숫자와 일치했다.

- Conv1: 45 tap×16 oc =720 byte, word0~44.
- Conv2: 144 tap×32 oc =4,608 byte, word45~188 및189~332.
- 합계: 720+4,608=**5,328=333×16**. 두 구간이 겹치지 않는다.

**C5 표현은 구분이 필요하다.** Conv 구간 자체에는 값 오류 검사가 없어 “Conv 구간 중간에 오류 발생”을 만들 수 없다. 이어지는 지시대로 Conv 뒤쪽 shift 검사 오류를 사용했다. Conv1 shift 실패는 이미 기록한 Conv1의720 byte를 보존하고 이후 Conv2 쓰기를 막는다. Conv2 shift 실패는 완료된 Conv 전체5,328 byte를 보존한다. 테스트만을 위해 내부 error 레지스터를 강제로 바꾸지 않았다.

또한 LUT 증가폭만으로 나눗셈기의 유무를 증명할 수는 없다. RTL에서 `/`·`%` 연산이 없고 tap/oc 카운터로 구현됐는지 확인하고, 실제 합성 자원도 함께 기록했다.

원문 r44의 blob 내부 `[oc][ic][kh][kw]` 순서는 이번에 확정하지 않았다. 아래 검증은 **지정된 스트림 순서에서 명세 주소식으로 scatter하는 회로**의 검증이며 실제 모델 blob·Encoder 연산까지의 golden 대조는 X-04 범위다.

## 3. 주소식과 실제 회로

| 항목 | 명세식 | RTL 구현 |
|---|---|---|
| Conv1 tap | n%45 | byte 쓰기마다 tap 증가,44에서0 |
| Conv1 oc/lane | n/45 | tap wrap마다 oc 증가, lane=oc[3:0] |
| Conv1 word | tap | `{1'b0,conv_tap_value}` |
| Conv2 tap | n%144 | byte 쓰기마다 tap 증가,143에서0 |
| Conv2 oc/lane | n/144, oc%16 | tap wrap마다 oc 증가, lane=oc[3:0] |
| Conv2 word | 45+(oc/16)×144+tap | `(oc[4] ? 189 : 45)+tap` |
| strobe | lane1개 | `16'b1 << oc[3:0]` |
| data | 해당 lane에 해당 byte | 128-bit 기본0, `[8×lane +:8]`에 byte 배치 |

START/reset에서 두 카운터를0으로 하고, **첫 Conv1 beat4와 첫 Conv2 beat118을 수락할 때 각 구간의 첫 쓰기 위치를 다시0/0으로 설정**한다. Conv2 첫 byte는 실제로 word45/lane0이다. 카운터는 Conv byte 쓰기가 성립할 때만 진행한다.

수락 에지에 `ld_data[7:0]`, 뒤의 WORK7cycle에는 보관한 `beat_data_reg`의 byte1~7을 쓴다. 따라서 같은 beat 안에서 tap44를 지나면 즉시 tap0/lane+1로 바뀐다. READY나 beat 처리 cycle을 추가하지 않았다. Conv 오류·reset 때는 write enable이0이다.

합성 RTL에 나눗셈·나머지·for/task/function/initial/generate/genvar가 없다. 동기 active-low reset과 현재값/다음값 분리를 유지했다. TB의 golden에는 의도적으로 `/`·`%`를 사용해 RTL 카운터 구현과 독립적으로 비교했다.

## 6. 합성 실패 원인·보정·최종 결과

같은 `loader_l02_synth` fixture와 `syn_check.tcl`, xc7z020clg400-1 /100MHz OOC 제약을 사용했다. 요청된 결합 합성1회에서 setup 위반을 발견해 수정 후1회를 추가했다. **실제 합성은 총2회**다.

| 대상 | LUT | FF | RAMB36 | RAMB18 | DSP | WNS(ns) | 래치/조합루프 |
|---|---:|---:|---:|---:|---:|---:|---|
| L-02 | 437 | 199 | 10 | 3 | 0 | +1.801 | 0/0 |
| L-03 최초 | 645 | 212 | 10 | 3 | 0 | **−0.016** | 0/0 |
| **L-03 최종** | **631** | **212** | **10** | **3** | **0** | **+1.365** | **0/0** |
| 최종−L-02 | **+194(+44.4%)** | **+13** | 0 | 0 | 0 | **−0.436** | 변화0 |

LUT 증가194개는 작지 않다. Conv tap/oc 카운터, byte 선택, lane 배치, word 주소·strobe 및 제어 회로가 추가됐다. FF 증가13은 tap8+oc5이다. 자원 증가는 보고하되, LUT 수만으로 “나눗셈기가 생겼다/없다”를 판정하지 않았다. 합성 대상 RTL에 division/modulo 연산0, 구현은 명시적인 증가·비교·wrap·bit선택이다. DSP는0이다.

최초 임계 경로는 `ld_data[24] → u_conv_weight_ram/mem_reg_0/ADDRBWRADDR[13]`, data path8.339ns,9 logic level이었다. `conv_pending`과 주소0 선택이 `error_next`에 묶여 있어 header/shift의 현재 입력 비교가 Conv 주소까지 이어졌다.

Conv 구간에서는 새 header/shift 오류가 생기지 않고, 마지막 추가 VALID 검사는 LUT 구간에만 해당한다. 따라서 **Conv 요청 판별을 새 오류 판정에서 분리하고, 공통 Conv 쓰기는 저장된 error_reg와 reset으로 차단**했다. Param/LUT 등 오류가 실제로 생기는 구간의 즉시 쓰기 차단은 유지했다. 외부 신호·state/READY·쓰기 cycle을 바꾸지 않은 논리 분리다.

최종 임계 경로는 `u_blob_decoder/beat_count_reg_reg[1]/C → u_conv_weight_ram/mem_reg_0/ADDRBWRADDR[13]`, data path7.985ns,8 logic level(CARRY4 2개 포함)이다. WNS는 최초 대비1.381ns 개선, LUT는14개 감소했다. 최종 setup failing endpoint0/TNS0이다.

RAM4종은 모두 유지된다: Conv2RAMB36, Param1RAMB36+1RAMB18, LUT1RAMB18, FCW7RAMB36+1RAMB18. LUTRAM0, 36Kb 환산11.5로 L-02와 같다. 배치·배선/hold 및 실제 보드 검증은 이번 범위가 아니다.

최종 합성 배치에는 기존 Common17-741 CRITICAL WARNING(Tcl store 권한), Timing38-242 WARNING(OOC clock), Vivado12-180 WARNING(래치 검색0개)가 있다. 최초본에는 Netlist29-101 floorplanning 안내도 있었고 최종본에서는 없어졌다. **시뮬레이션 compile/elaboration 오류·경고0과 구별한다.** 최초 timing 실패를 최종 성공 로그로 덮지 않고 둘 다 보존했다.
